# 第13C-G步：受控学术检索与来源抓取

## 这一阶段解决什么问题

13C-F 已经给 verifier 令牌和读取 Bundle 的入口，但只能读取已经由可信调用方预存的 retrieval receipt。本阶段把网络能力限制成一个很小的后端边界：只允许固定学术域名，只发 GET，只允许固定 search provider，最多跟随三次重定向，响应体最多 1.5MB。

网络响应先保存为 hash-linked receipt，再把有限摘要和 evidence unit 返回给 verifier。原始 `responseText` 不从 search/fetch 接口直接返回。

## 与原仓库的对应关系

| 原仓库 | 学习版 | 作用 |
| --- | --- | --- |
| `goal-verification-access.ts:controlledFetch` | `goal-verification-evidence.mjs:controlledFetch` | HTTPS、allowlist、手动重定向、响应大小和错误分类 |
| `goal-verification-access.ts:searchUrl` | `goal-verification-evidence.mjs:searchUrl` | 构造 OpenAlex、Crossref、Europe PMC 固定查询 URL |
| `GoalVerificationAccessService.search` | `goal-verification-evidence.mjs:search` + `access.search` | token 授权、抓取、保存 receipt、解析有限检索结果 |
| `GoalVerificationAccessService.fetchSource` | `goal-verification-evidence.mjs:fetchSource` + `access.fetchSource` | 读取允许来源并生成受限 evidence unit |
| `GoalEvidenceAccessError` | `goal-verification-evidence.mjs:GoalEvidenceAccessError` | 区分来源不存在和 provider 不可用 |
| `goal-verification-api.ts` | `apps/api/router.mjs` 的 `search/fetch` 路由 | 将网络访问限制在 token-scoped POST 接口 |

参考实现还会调用 `EvidenceResolver.materializeRetrieval()`，生成持久、随机、可去重的 evidence unit。本学习版目前返回带 retrieval receipt ID 的临时 unit，持久 Evidence Resolver 仍是下一阶段。

## 逐文件解释

### `goal-verification-evidence.mjs`

`controlledFetch()` 接收 URL、可选 `AbortSignal` 和可注入的 `fetchImpl`。注入点让测试可以用假 fetch 验证所有边界，不需要真的访问互联网，也不会产生模型或网络费用。

每次请求检查：

- 协议必须是 `https:`；
- 主机必须是 `api.openalex.org`、`api.crossref.org`、`www.ebi.ac.uk`、`europepmc.org`、`pubmed.ncbi.nlm.nih.gov` 或 `doi.org`；
- 请求方法固定为 GET；
- 重定向手动处理，最多 3 次，每次重新检查协议和主机；
- `Content-Length` 超过 1.5MB 立即拒绝，没有长度时用流式 reader 累加并在超限时 cancel；
- 404 变成 `EVIDENCE_NOT_FOUND`；429、5xx 和网络错误变成 `EVIDENCE_PROVIDER_UNAVAILABLE`。

`search()` 只接受 OpenAlex、Crossref、Europe PMC，查询限制为 1–1000 字符，返回数量限制为 1–20。服务端只提取有限结果条目，每个条目最多保留 16,000 字符摘要，并去掉数据库保存的 `responseText`。

`fetchSource()` 用于读取具体 DOI、PubMed 或允许域名 URL。它保存最终 URL、provider、时间、内容类型和 SHA-256 receipt，再返回有限文本摘要。空响应返回 `evidenceStatus: not_found`，不会伪造可引用事实。

### `goal-verification-access.mjs` 与 `apps/api/router.mjs`

访问服务先调用 `store.authorize()`，再委托 evidence 层执行 search/fetch。新增两个 POST 路径：

```text
POST /v1/goal-verifications/:id/search
POST /v1/goal-verifications/:id/fetch
```

路由只接受 POST，验证路径 ID、access token 和请求体；provider、query、limit、url 的业务约束由访问层再次检查。provider 不可用返回 502，来源不存在返回 404，错误 token 仍返回 403。

## 数据流

```text
Verifier 携带 verificationId + accessToken
          │
          ▼
access.search / access.fetchSource
          │  authorize(status=running)
          ▼
controlledFetch（HTTPS + allowlist + redirect + 1.5MB）
          │
          ├─ SQLite verification_retrievals
          │    responseText + sourceUrl + contentSha256
          │
          └─ 有界 evidenceUnits + resultCount/status
               （不返回 responseText）
```

数据库保存完整 responseText 是为了之后复核“当时取得了什么”；它不等于把全文直接暴露给模型。模型只能看到后端裁剪后的 evidence unit。

## 测试与当前边界

新增测试先在未实现 `search/fetch` 时失败，之后通过 fake fetch 验证 OpenAlex URL 参数、GET/manual redirect、allowlist、三次重定向上限、1.5MB 流式上限、receipt 保存和 raw response 隐藏。本阶段没有主动访问真实互联网，也没有调用 MiniMax 或 Agent Compose。

当前还缺：

1. 持久 Evidence Resolver，把临时 `retrieval:<id>:<index>` 替换为随机、去重、可重放的 evidence ID；
2. `attempt` 读取和 retry feedback；
3. 真实 Agent Compose verifier，将 prompt、工具 schema、search/fetch 和 review protocol 接起来。

下一步先实现 Evidence Resolver 的数据库表和 `prepareBundle/materializeRetrieval/materializeCheck`，让 policy 只接受后端持久化的 evidence unit。
