# 第10C步：把工具成品登记为一份待验证提案

## 一、这一轮解决的问题

第10B步已经获得了真实工具镜像，以及带runtimeArtifact的提案副本。但系统还没有一个可以长期查询的“提案登记簿”。后续的验证报告、批准版本和调用记录，需要知道自己对应哪一次提交。

本轮增加提交、列表和按编号查询。提交时保存独立材料快照并分配提案UUID，登记为submitted；查询时检查保存材料与登记摘要是否一致。这些操作不执行候选或基线，不连接模型，也不把构建时的案例结果自动转换为正式验证成绩。

## 二、对应原仓库的哪些文件

参考版本仍为application965c53f/checkout67d2754。应用实现独立编写，只沿用其职责和可观察格式。

| 原文件 | 原职责 | 本轮对应文件 |
| --- | --- | --- |
| packages/capability-platform/tool-proposals.ts | 将提交输入保存成manifest与候选/基线源文件，读回核对 | tool-proposals.mjs |
| packages/capability-platform/tool-registry.ts | SQLite提案、事件以及后续验证/版本管理 | tool-registry.mjs，仅提交和查询部分 |
| packages/capability-platform/tool-lifecycle.ts | 串联合同检查、材料保存、冻结和登记 | tool-lifecycle.mjs，仅提交和读回部分 |

原submitRegisteredToolProposal本身不执行代码；原HTTP提交接口还可以登记自动化并异步启动维护流程。本学习步骤只有可信CLI，没有接入那段自动化，因此提交后不会自动运行验证或批准。

本轮选择SQLite记录索引，材料单独保存在目录中。这样既能用数据库查询状态和提交事件，又能直接打开文件学习源码、测试与镜像说明。将所有内容混为一份可改写JSON索引，不利于后续关联多次验证；一次引入全部审批功能又会掩盖提交这一步的意义。

## 三、tool-proposals.mjs：制作材料快照

createToolProposal接收第10B步生成的完整提案，先使用现有checkToolProposal检查，再创建新的UUID目录。readToolProposal负责按ID重新读取，并核对材料。它们没有执行源码的入口。

教学工具的材料目录结构如下：

```text
runtime/tool-artifacts/proposals/<proposalId>/
  manifest.json    工具说明、测试、权限、镜像和源文件摘要
  tool.mjs         候选实现，即希望纳入管理的新工具
  baseline.mjs     比较对象，后续独立验证才使用
```

manifest把原提案中的script替换为scriptFile和scriptSha256；baseline也拆为独立文件及摘要。smokeInput、testCases、benchmarkCases、permissions和runtimeArtifact继续保留。源码字节不因保存而改写。

保存阶段还会拒绝不能无损往返UTF-8的候选/基线字符串，避免编码时被静默替换；这是比字段预检更严格的材料保存条件。正常中文、BOM和CRLF按原字节保留。

这里有两种摘要：scriptSha256对应一个源文件，artifactSha256对应整个材料包。后者按文件名排序，把文件名、NUL分隔符和实际文件字节送入SHA-256，所以修改测试预期、替换基线或增加文件也会改变材料身份。它与Docker镜像的imageDigest是三个不同对象的指纹，不能互相替代。

Linux上完成的材料文件设为0400，目录0500，只让所有者读取；原项目使用0444/0555，本学习版进一步限制其他用户读取。拥有文件的用户仍能改权限，所以“只读”只防误操作，查询时仍需重新核对摘要。Windows不承诺同样的POSIX权限效果。

## 四、tool-registry.mjs：写入登记簿

数据库位于runtime/tool-registry/registry.sqlite，独立于网页任务数据库。它使用已有Node内置SQLite，无新依赖。

tool_proposals保存提案ID、稳定工具名、状态、材料路径/摘要、权限档位、镜像摘要和时间。tool_events保存proposal_submitted提交事件，记录actor=local-cli，表示本轮由可信命令提交。

提案行与事件必须同时成功。registerProposal在BEGIN IMMEDIATE事务中写入二者，任一步失败就ROLLBACK。测试用真实SQLite触发器故意阻止事件插入，检查提案行也没有留下；不会出现“登记成功却没有提交事件”的半条记录。

数据库构造必须明确指定路径。已有数据库需要符合本模块的类型标识与版本，不能把一个无关SQLite文件当作新登记簿迁移；链接文件也拒绝。查询使用readOnly模式，不创建不存在的数据库或执行schema迁移。

## 五、两个状态为什么不同

| 位置 | 当前值 | 含义 |
| --- | --- | --- |
| manifest.status | draft | 这是一份尚未发布的候选材料 |
| manifest.version | 0.1.0-draft | 草稿格式中的版本标记，不是工具已发布版本 |
| registry.state | submitted | 系统已经接收并登记该提案，等待后续验证 |
| verified / approved / activated | false | 本轮没有执行完整验证、批准或激活 |

toolName是能力的稳定名称；proposalId标识某一次提交；buildSessionId标识前一步某次构建。一个工具名称可以对应多份提案，而一次镜像构建与一次提交也不是同一个编号。

与原项目一致，重复提交相同材料会分配新UUID，不按内容去重。重新尝试submit前应先看上次输出和list。当前尚无正式版本管理，含parent的更新提案会明确拒绝，不会默默丢弃父版本关系。

## 六、tool-lifecycle.mjs与CLI：把步骤连起来

submitRegisteredToolProposal依次完成完整合同检查、创建材料、写入登记。listRegisteredToolProposals读取最近最多100条元数据；getRegisteredToolProposal按编号定位固定根下材料，核对源文件、整包摘要以及数据库中的工具名/权限/镜像与manifest相同，然后返回详情和提交事件。

数据库里的artifactPath也要核对，不能直接用它读取任意路径。材料目录只允许固定文件集合，拒绝额外文件、子目录、链接、错误ID和超限数据。列表只列元数据，不声称每份材料都检查通过；show才执行材料完整性读回。

使用已有Node24，进入唯一服务器项目根后运行：

```sh
cd /home/hanwen/Project/project/siNRA-pi
npm run tools:proposals -- submit runtime/tool-builds/7e0aa187-6c67-46b6-8c5f-7b2e4f5351ea/proposal.json
npm run tools:proposals -- list
npm run tools:proposals -- show <提交返回的proposalId>
```

submit会新增持久记录；list/show不运行工具。命令限制Linux/hanwen/指定项目根，不能通过sudo或环境变量改用其他目录。输入沿用上一轮受限读取函数，错误信息不回显源码，详情也不包含源码正文。

文件系统和SQLite之间没有一个共同事务：完整材料先保存，然后登记数据库。如果数据库失败，可能留下未登记的材料包，错误会返回该包ID与路径；不自动删掉它，也不把它显示成submitted。进程崩溃恢复、幂等请求和孤立材料管理留待相应阶段。

## 七、验证边界

本轮检查的是“提交材料保存后有没有变”，不证明材料中的算法正确，也不验证声明镜像是否存在或镜像代码与源码相符。runtimeArtifactVerified仍为false；对正式产物进行独立验证是下一阶段的职责。
