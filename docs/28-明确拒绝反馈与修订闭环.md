## 1. 为什么这一轮先修错误反馈

上一节的 Pi 已经做出了能正确计算极值的新源码，调试也成功了，但提交时自己增加了 `parent`。旧候选没有这个字段，因此它改变了本轮禁止改变的合同，被后台拒绝。

Pi 收到的却是：“工具构建调用失败；操作可能已经完成。”它随后怀疑后台宕机，调用其他不适用的接口作诊断，最终没有登记替代候选。

这里要分开两个问题：模型为什么改变了不该改变的字段，以及程序为什么没有清楚告诉模型拒绝原因。本轮明确 `parent` 的含义，并修复第二个问题。好的反馈可以让 Agent 知道哪些动作有依据，但不能保证模型一定正确理解或改对。

## 2. parent 与修订谱系不是一回事

假设某工具已经批准发布为 `1.0.0`，现在做 `1.0.1` 的候选，`parent` 指向那个真实存在的正式父版本。这用于版本升级和父源码比较。

而一个验证失败、从未发布的候选，没有凭空变成 `1.0.0`。修订候选和失败候选之间的关系，由宿主保存的 `previousProposalId`、`rootProposalId`、`attempt` 表示。

```text
正式版本关系：已发布版本 1.0.0 ← parent ← 升级候选
修订关系：    失败候选 A ← previousProposalId ← 替代候选 B
```

因此，原提案没有 `parent`，修订时继续省略；原来有，就保持相同正式父身份。不能为了表示“这是修订版”而新增 `parent`。

## 3. 原仓库怎样处理提案错误

参考 `packages/capability-platform/tool-contract.ts` 的 `toolContractIncompletePayload()` 和 `toolProposalInvalidPayload()`，将错误整理为代码、原因、合同要求和下一步动作。参考 `src/mcp-server.ts` 把它作为 `isError: true` 的工具结果交回 Pi。

参考中央提交路由在 `apps/api/router.ts`，远程调用在 `packages/domain/sirna-tools/sirna-tools.ts`。后者读取 HTTP 错误说明再抛出，MCP 层再包装，所以原版也不是所有层都原样保留 JSON，但 Agent 能得到比“不可用”更具体的原因。

个人版学习这一职责，采用更窄的安全反馈：只报告本轮已明确识别、且发生在登记之前的合同冲突。任意系统异常、源码内容、字段实际值、宿主路径和堆栈都不能直接传给 Agent。

## 4. 一次错误怎样从宿主回到 Pi

```text
修订服务比较冻结合同
 → 构建会话确认仍在登记意图之前
 → 私有 HTTP 接口生成固定错误响应
 → relay 转接有限、可识别的错误
 → guest 客户端检查响应类型与大小
 → MCP 返回 isError:true
 → Pi 读取原因并决定下一步
```

程序能证明“没有登记”的依据，是拒绝发生在 `proposal_submit` 记录和真正登记函数之前。此时修正请求字段并再次提交，与网络中断后盲目重试有本质区别：后者不知道前一次是否已经登记。

| 情况 | 程序知道什么 | Agent 应如何处理 |
| --- | --- | --- |
| 可信修订合同冲突，在登记之前拒绝 | 本次没有登记；给出固定字段名 | 按原合同修正请求，再提交；不改变已经冻结的源码与产物 |
| 超时、断线、未知异常或不完整错误响应 | 无法确认最终结果 | 先核查宿主记录，不能自动重放 |
| 成功返回新 proposalId | 候选已经登记 | 仍须独立验证，不能宣称已经批准或启用 |

“未登记”只描述这次提案提交，不表示之前的构建、调试和镜像打包没有发生。这些已完成的产物仍然保留。

## 5. 本轮教学的范围

复用第10N节的教学草稿，换用全新的任务和工具名 `summarize_numeric_range_repair_feedback`。人为给定的根源码依然错误地把首尾当成极值。先构建并提交，再独立验证失败，然后显式请求一轮修订。修订若产生合法新候选，再独立验证一次，最后结束任务。

根和替代候选必须使用相同测试、相同基线、相同权限和相同净增益门槛。新源码由这一轮 Pi 生成；它自己的调试结果不代替外部验证报告。第10N节旧失败记录不恢复、不改写、不补交。

每个网页消息内部可能有多次模型响应与工具调用。“一轮修订”不是“一次模型调用”，三代谱系上限也不是 token 或费用上限。本例是有明确边界的工程教学，不是隐藏测试、独立泛化或自进化有效性研究。

## 6. 结合代码逐层理解

### 第一步：比较合同，但不直接向外发送内部异常

[`tool-repair-contract.mjs`](../packages/capability-platform/tool-repair-contract.mjs) 的 `assertRepairContract()` 比较原候选和新候选的冻结字段。原先只抛一个笼统异常，现在能指出差异字段，例如 `['parent']`；字段的实际内容不进入错误。原候选和替代候选仍必须采用不同构建会话，缺省 `minNetGain` 仍按 1 解释。

[`tool-repair-service.mjs`](../packages/capability-platform/tool-repair-service.mjs) 的 `registration()` 先确认当前任务、运行编号、修订票据和来源材料，之后才进行合同比较。身份不匹配时不能借机向调用者解释其他任务的合同。

同文件 `promptFor()` 新增 parent 的直白说明，以及明确拒绝和未知结果的不同处理。它没有替模型写好修复源码，也没有降低测试门槛。

### 第二步：证明拒绝发生在“开始登记”之前

[`tool-build-sessions.mjs`](../packages/capability-platform/tool-build-sessions.mjs) 的 `propose()` 是这个证明的关键位置。它已经确认源码和 `runtimeArtifact` 与本轮 finalized 产物相符；接着调用修订登记政策。只有此处的合同拒绝能被确认为“本次未登记”。

一旦准备写 `proposal_submit`，就先标记本会话已经尝试提交。从此之后，即使写日志、登记、保存结果或再次读回失败，也只能报告未知，不能继续使用“未登记”的承诺。否则 Agent 可能因错误提示重做一份实际已经登记的候选。

### 第三步：用一个小合同贯穿 HTTP 与 MCP

新增 [`builder-rejection.mjs`](../packages/domain/sirna-tools/builder-rejection.mjs) 定义公开错误合同和内部身份标记。内部用三个独立的 WeakMap 区分“发现合同冲突”“已确认发生在登记前”“已校验的远端反馈”。WeakMap 可以理解为程序私有的关联表；在任意 Error 上自己填 `code` 或 `outcome`，不会获得同样资格。

HTTP 响应的完整形状是：

```json
{"error":{"protocolVersion":"sirna-builder-rejection/v1","code":"repair_contract_mismatch","outcome":"not_registered","fields":["parent"]}}
```

[`tool-build-api.mjs`](../apps/api/tool-build-api.mjs) 仅对 propose 的已确认错误生成 HTTP 409；其他错误继续交给原网关的通用处理。宿主调用事件依然记录 `success:false`，不会把“成功传达了拒绝”误写成“工具提交成功”。

[`relay.mjs`](../containers/agent-tools-relay/relay.mjs) 只接受这一种专用 409、固定字段和最多 2048 字节，再重新构造响应。它仍是单文件挂载，不需要获得注册表、Docker 或模型凭据。

[`tool-builder-client.mjs`](../apps/mcp/tool-builder-client.mjs) 在 guest 中再次检查状态码、JSON 类型、UTF-8、字段和大小，才建立本地已校验错误。状态为 201 却带错误对象，也不能假装成功。超时、断流、未知状态和畸形响应继续隐藏原文，且不自动重试。

[`approved-server.mjs`](../apps/mcp/approved-server.mjs) 虽然名字含 approved，但它也是 guest 内正式工具和构建工具共用的 MCP 适配器。这里将专用错误转为 `isError:true`，给 Pi 固定的修正指导；普通错误仍提示查宿主记录。

### 第四步：让新任务实际用到新代码

[`agent-compose.yml`](../agent-compose.yml) 改用新项目 identity `sirna-pi-learning-builder-feedback` 和新 guest 标签 `sirna-pi-guest:pi1.2.0-mcp4`；[`build-project-guest.sh`](../scripts/build-project-guest.sh) 对应构建此标签。[`.dockerignore`](../.dockerignore) 只增加新错误模块的许可，继续排除运行数据、凭据与宿主构建内核。

只改宿主磁盘上的 client 不够，因为 Pi 用的是镜像内部文件；所以需要重新构建 guest。新任务使用新镜像，旧任务仍保留原版本。relay 和网页后台也必须在空闲时重新加载代码。

新任务 `d72bc8cc-ea17-4782-a4e6-230042dafff8`，执行会话 `c8fa3878-ebed-4bbc-aca3-bd87423f81c7`。通过网页发送一条根构建消息，在根候选验证失败后点击一次“请求一轮修订”，得到一个新候选，然后只对这个替代候选验证一次。

根源码由教学草稿指定。Pi在修订轮改变源码与说明，另建构建会话，重新打包；没有改变测试、基线、权限、运行时、净增益门槛或缺省parent。宿主保存 `attempt:1` 和指向根候选的 `previousProposalId`，修订票据变为 `superseded`（已登记替代）。这表示旧候选有了后继，不表示旧负报告被覆盖或旧候选变成通过。

两轮各做1次排序输入调试，再各做1次独立验证。每次独立验证包含9次业务执行和2次语法检查。新旧候选都能通过排序调试，只有独立乱序案例揭示差异，这正是不能把“Agent说调试成功”直接当作验收的原因。

## 10. 下一步为什么是Curator

现在已经能处理“某个工具候选失败了，怎样把证据交给Agent修订，并重新验证”。但这份数值工具最初由我们指定，系统还不会从日常任务轨迹中发现“这里反复写了同样代码，适合封装一个工具”。

参考仓库的 `packages/extensions/tool-curation/tool-curation-coordinator.ts` 负责组织这种轨迹到能力建议的过程；已提交提案的验证与修复属于automation/maintenance。下一步应沿这条职责学习轨迹如何筛选、能力建议如何生成和去重、哪些条件才派发构建，再复用已经完成的构建与验证链路。

本轮是一个已知缺陷、可见测试、弱教学基线上的受控修订成功。它不证明工具在任意输入下正确，不证明隐藏任务泛化或稳定自进化优势，也不等于完整复现Curator。原仓库自动批准与个人版人工批准门的差异继续明确保留。
