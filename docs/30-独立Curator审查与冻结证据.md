# 第11B步：独立Curator审查与冻结证据

第11A步让程序整理“这轮任务反复用了什么能力”。本步要接上的，是“这件反复发生的事，是否值得变成一个可复用工具”。Curator就是负责这个判断的审查Agent。

## 先理解它增加了什么

假设任务中三次查询同一类数据，而且输入并不相同。上一轮的规则只能说：这里出现了重复。它不能可靠判断三次查询是否属于同一个稳定能力，现有工具能否替代它，或者封装起来是否只是重复造轮子。

现在把工作分成两部分：程序负责收集、固定、检查证据；模型负责解释这些证据、提出建议。模型可以回答skip（跳过），也可以回答candidate（建议一个能力）。这里的candidate是审查建议，不是工具登记库中的submitted提案；它还没有代码、镜像、独立验证或发布资格。

这一阶段的链路是：

```text
已结束任务的事件记录
  → 11A规则预览
  → 用户显式送审并携带预览摘要
  → 后台重新核对同一份来源
  → 保存固定证据与审查请求
  → 独立、无工具的Pi会话
  → 检查回答格式、身份、证据引用
  → 保存“跳过”或“建议”并在网页查看
```

这个顺序有实际意义。不能先让模型回答，再根据它的答案挑选证据；也不能把模型说“值得做”解释为工具已经正确实现。

## 为什么需要冻结

网页预览是临时计算的。用户看完后，正式工具目录可能更新，任务也可能又进行一轮。如果后台随手读取“最新记录”，送给模型的就可能不是用户刚刚看到的内容。

因此送审带三个值：runId指定轮次，sourceSha256绑定保存的来源与规范化工具目录，previewSha256绑定当时显示的预览。目录先去掉MCP的sirna_tools_前缀、去重并排序，这份相同的名称列表既参与摘要，也送给Curator；别名前缀不代表另一种能力。后台重新计算，一致才接受；不一致则要求重新读取预览。SHA-256在这里是内容指纹，不是正确性评分，也不是原始模型请求的签名。

接受后创建独立curationId，把证据及traceSha256一起保存。后面的等待、执行、成功、失败更新只改变状态和结果，不改证据。模型回答必须带回同一个curationId和traceSha256，程序才能确定“这份回答是对这份材料作出的”。

这也解释了为什么要分别记录三个编号：taskId是原业务任务，runId是我们观察的那一轮，curationId是针对它新建的审查。审查本身还有独立会话与执行编号。它们不能混用，否则失败时就可能停止错误的任务，或者把另一轮回答放进当前审查。

11A最多显示12次业务调用。规则可能在完整轮次中发现重复，但触发依据已经落在窗口外。本步要求至少一个完整保留的触发组；不能因为eligibleForReview为true，就把不完整窗口当成充分依据。最终冻结材料还受64KiB限制，超限拒绝，不悄悄删除关键依据。

## 文件怎样分工

| 文件 | 输入与工作 | 这层存在的原因 |
|---|---|---|
| `packages/extensions/tool-curation/tool-curation-preview.mjs` | 一次读取任务事件和正式工具目录，同时生成预览与内部快照 | 防止预览和送审读取不同的目录 |
| `tool-curation-evidence.mjs`（同目录） | 从完整触发组建立trace/v1并计算指纹 | 把临时显示内容变成固定审查材料 |
| `tool-curation-result.mjs`（同目录） | 生成审查提示、解析并校验skip/candidate | 模型文本不能直接当作可信程序指令 |
| `tool-curation-store.mjs`（同目录） | 保存请求、证据、状态、执行身份和结果 | 刷新或进程退出后仍可追溯；重复点击不重复付费 |
| `tool-curation-service.mjs`（同目录） | 接受请求、串行派发、处理失败和关闭 | 把一次HTTP点击和可能持续几分钟的执行分开管理 |
| `agent-tool-curator.mjs`（同目录） | 新建独立会话，等待完整终态，释放新guest | 审查不借用原任务的上下文和操作权限 |

| `agent-compose-curator.yml` | 声明单独的Compose项目、模型与Curator镜像 | 让新审查与原任务的配置和容器分开 |
| `containers/agent-compose-guest/Dockerfile.curator`、`pi-curator.sh`、`curator-guard.mjs` | 在现有镜像上增加无工具启动方式和调用拦截 | “只读”要由程序限制，不能只靠提示词 |
| `apps/api/bootstrap.mjs`、`router.mjs` | 组装服务，提供提交、列表、详情接口 | 网页只依赖明确接口，不直接操作数据库或模型 |
| `public/curation.mjs` | 展示预览、显式送审、手动刷新与查看建议 | 区分规则线索、模型建议和正式工具 |

## 数据库保存什么

旧任务仍在runtime/tasks/tasks.sqlite。审查使用自己的runtime/tool-curation/curation.sqlite，不把建议写进正式工具登记库。原版把Curator表放进任务数据库；学习版沿用相同职责与状态，但使用独立文件，便于逐步增加模块并核对旧数据未变。

状态遵循原版waiting→running→skipped/candidate/error。唯一约束把taskId与runId绑定，重复相同请求返回已有审查；不同摘要不能覆盖旧审查。同一时刻只有一个消费者派发。

“服务中断后重试”对模型请求并非总是安全：网络断开时，服务端可能已经接收并计费。因此重启会把未完成请求记为结果未确认，不自动再发一次。身份和材料保留供检查。若停止或容器释放未确认，暂停新的审查，避免把不确定状态当成空闲。

数据库路径还会拒绝符号链接和多重硬链接，SQLite的WAL、SHM、journal辅助文件也一样。硬链接可能让两个文件名指向同一份内容；若其中一个被SQLite当日志写入，另一个“无关文件”也会改变。这是本机数据保全检查，不是模型语义检查。

## 独立Agent究竟独立在哪里

底层仍是Pi1.2.0和MiniMax-M3，并没有训练一个新模型。独立的是角色、会话、记录目录和容器。它得到的是脱敏后的冻结材料，不会接管原任务的聊天会话，也不获得原任务的MCP连接租约。

管理容器原本只直接挂载普通任务的agent-compose.yml。新角色的配置由compose-executor.mjs复制到项目内runtime/agent-compose/data/curator-config/agent-compose.yml；管理容器通过已经存在的/data挂载读取它。复制采用“首次创建，之后必须逐字节相同”的检查，遇到陌生内容就拒绝覆盖。这样本轮增加配置不需要重建管理容器。以后修改这份配置时，需先在空闲状态明确处理旧副本，不能把静默覆盖当作正常升级。

专用wrapper关闭工具与自动资源加载，并显式加载guard。仅有空工具列表还不够：模型可能编造工具调用，而Pi遇到未知工具时可能把错误再交回模型，形成第二次请求。guard因此先检查模型完整消息：出现toolCall就保留原内容、把终态标为aborted并在容器内立即中止；执行开始和tool_call处还有兜底阻止。它还限制provider请求次数。Compose与Pi为了运行仍需写自己的会话日志，所以“只读审查”指不执行任务操作，不代表服务器完全没有文件写入。

审查适配器180秒后发出取消，独立RPC传输也设置180秒截止时间，零自动重试；启动和清理另有等待，因此整个HTTP后台作业并不保证恰好180秒内结束。独立RPC解决了一个特殊情况：服务端尚未返回执行编号时，还不能按编号停止，不能继续沿用普通任务的600秒传输默认值。包装器必须检查成功终态和最终回答；仅仅await一个函数返回，不代表模型成功完成。原运行器会将部分异常记录为error事件，因此包装器还要检查这些事件。最后只释放本次新guest并保存记录，不删除原任务容器或旧会话。service-lifecycle.mjs负责等待已接受工作结束，并在某个关闭动作失败时仍尝试关闭其他数据库和两个RPC连接。

## 程序检查什么，模型判断什么

程序检查协议、审查编号、证据指纹、大小限制、候选字段、权限草案、工具名称和事件引用。模型如果引用冻结材料之外的事件，或者建议已经存在的同名工具，结果会被拒绝。回答最多48KiB；必须是一个JSON对象，不从大段正文中猜测哪一段是答案。解析采用JSON.parse，不额外实现通用重复键检测。

模型判断是否存在值得复用的能力、它的边界是什么、现有工具为什么不够，以及输入输出应该怎样约定。即使这些字段全部通过检查，也只能说明“建议符合提交合同”，不能证明解释真实、封装有收益或工具会工作。

例如permissions.profile是权限建议，不是授权操作。它写controlled_network不代表程序会马上开放网络；后续Builder、验证器和批准流程仍需分别检查。

## 与原仓库的关系

参考固定为sirna-pi-agent-service-refactor@67d275494c50f1e5c205b96b72a7b1623acfbe1d的tool-curation目录、独立tool-curator配置及guard。代码按职责独立实现，不整段复制。

本步保留原版trace/result协议主字段、独立审查角色和状态分工，增加来源指纹、完整线索约束和更明确的失败处理。原版attachVerificationContext会重写已经保存的trace/hash；本步不提供这种更新，避免模型持有旧材料、数据库却变成新材料。后续验证信息不能反向改写这一份已冻结审查。

原版还会自动观察任务、处理report_tool_gap、按能力去重，并将建议交给Builder。本步先完成手动可观察的审查过程，这些自动触发与构建连接放在后续阶段；也没有自动批准。
