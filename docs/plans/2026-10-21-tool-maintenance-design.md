# 第10L步：网页候选验证作业设计

## 目标和依据

承接第10K步网页 Pi 提交的工具候选，让人能在网页查看候选、明确发起独立验证，并查看持久结果。用户已要求沿原仓库逐步实现、个人仓库只用 main；本轮继续该已授权方向，不新增分支。

参考固定版本 `67d275494c50f1e5c205b96b72a7b1623acfbe1d` 的 `apps/api/router.ts` 中 `/v1/tool-proposals`、`/:id/validate`、`/:id/validation-summary`，以及 `packages/capability-platform/tool-maintenance-worker.ts` 与注册表维护作业函数。保留候选、作业、验证报告的职责分离和异步 202 接受语义。

原版 Curator 从任务轨迹提出能力建议；已提交提案的验证/修复/批准属于 automation。此次只完成维护作业与网页验证入口，不声称完成 Curator、自动修复或自动发布。原版自动流水线会批准合格候选；学习版继续保留已有人工批准边界。

## 本轮行为

1. 全局候选面板列出提案及最新维护作业，不与当前聊天任务混淆。
2. 人点击验证，POST `/v1/tool-proposals/:id/validate` 接受一次明确请求，返回 202 和持久作业。只接受 submitted / verification_failed；相同未完成作业去重。请求使用稳定 UUID 幂等键，网络重试不重复创建作业；同一键不能用于不同候选。
3. 单一后台 worker 逐个领取作业，复用现有 `validateRegisteredToolProposal` 与 Docker runner；不调用模型、不赋予 Pi/MCP 验证或批准权限。
4. 作业 pending → running → succeeded / failed。succeeded 仅代表验证流程完成，报告 passed 才表示通过；完整不通过报告仍属作业 succeeded。基础设施错误属 failed。启动时旧 running 标为 interrupted，同时在同一事务持久暂停队列；因为进程崩溃后原Docker容器可能仍存活，已有pending也须等待可信检查。只有pending而没有running遗留、且队列未暂停时可继续。显式新请求也不能绕过暂停；检查处置后才能重试。
5. 作业使用项目内独立 SQLite 文件，避免改写现有注册表 schema4；这是相对原版同库维护表的简化差异。领取事务与约束保证至多一个 running；不确定执行失败的 failed 与暂停也在同一事务提交，避免失败已保存而暂停丢失的崩溃窗口。公开响应只给固定安全字段，原始执行日志留在 runtime。
6. 网页通过 GET 刷新列表与验证摘要；摘要来自已有完整性核验过的报告，不接受网页传来的成绩。显示检查状态、样例通过数、candidate/baseline 分数与净收益、报告标识，不公开服务器路径或原始执行输出。
7. 正常关闭先停止接受/领取新作业，等待已开始的验证落盘再退出；浏览器刷新、断连不会取消已接受作业。等待任务/工具调用的原有关闭顺序保留。

## 验收和边界

- 真实 FS/SQLite/HTTP 的测试覆盖去重、状态区分、串行、重启、不完整报告、错误脱敏、正常关闭；Docker 为外部测试替身，服务器再做真实容器验收。
- 真实网页仅为第10K候选 `26883ce8-5c2e-4a0e-90fb-d96e53270b9c` 发起一次验证。核对页面与报告、数据库记录、执行日志一致；不假定结果必过。
- 保留旧提案/报告/版本、材料、正式工具目录、任务历史、会话和四个旧运行容器。允许所选提案的状态、latest validation、更新时间及相应追加验证/事件改变。
- 不修改凭据、不调用模型、不自动批准/激活、不扫描后自动验证其他候选。实现后独立复审、双端检查、项目内重启和学习文档，再提交同步三处 main。
