# 第 1 步 A：把 Pi 安装到服务器

日期：2026-10-15。本页记录已经完成的安装阶段；首次真实模型任务尚未开始。

## 这一步解决什么问题

Pi 是需要运行在某台计算机上的程序。我们先把这套程序和它所需的依赖放到指定服务器，建立可以重复运行的命令入口。

- **Node.js**：执行 Pi 的 JavaScript 程序的运行环境。
- **npm**：下载、安装和管理程序依赖的工具，随 Node.js 提供。
- **Pi**：已经实现模型连接、工具和 Agent 执行循环的软件。
- **大模型服务**：后续由 Pi 调用、负责生成回答和选择工具的服务。本轮没有配置或调用。

安装 Pi 不会下载大模型权重，也不会自动产生一个网页。

## 新增文件分别做什么

| 文件 | 作用 |
| --- | --- |
| `package.json` | 项目的依赖清单和命令菜单；声明使用 Pi 1.2.0，要求 Node.js 至少 22.19.0 |
| `package-lock.json` | npm 生成的精确依赖记录及完整性信息，使后续安装使用同一组依赖版本 |
| `.nvmrc` | 告诉 nvm 本项目使用 Node.js 24.16.0；进入目录后仍需执行 `nvm use` |
| `.npmrc` | `engine-strict=true` 让不满足版本要求的安装报错；`save-exact=true` 让以后添加依赖时记录明确版本 |
| 本文 | 解释安装位置、命令和实际验证范围 |

`private: true` 防止把这个学习项目误发布为 npm 软件包。GitHub 仓库是否私有是另一个独立设置。

`package.json` 的三个命令只是启动 Pi 的快捷入口，尚未实现我们自己的 Agent 封装：

```json
"scripts": {
  "pi": "pi",
  "pi:version": "pi --version",
  "pi:help": "pi --help"
}
```

执行 `npm run pi:version` 时，npm 找到本项目 `node_modules/.bin/pi`，再由当前 Node.js 运行它。`npm run pi` 则会进入交互程序，留到模型配置阶段使用。

## 在服务器上怎样运行

先在 Windows 终端连接：

```powershell
ssh -p 1369 hanwen@39.96.171.247
```

进入服务器后：

```bash
cd /home/hanwen/Project/project/siNRA-pi
source /home/hanwen/.nvm/nvm.sh
nvm use
node --version
npm --version
npm run pi:version
npm run pi:help
```

服务器非交互 SSH 默认找到的系统 Node 是 12.22.9，不能用于本项目。因此，自动执行时显式选用已有 Node 24，交互使用时执行上面的 `nvm use`。不修改系统 Node，也不改其他项目的默认配置。

从 Git 源码重新安装依赖时，在选好 Node 并进入项目目录后执行：

```bash
npm ci --ignore-scripts --no-audit --no-fund
```

`npm ci` 按锁文件进行干净安装，会替换当前项目已有的 `node_modules`；它不会删除源码。`--ignore-scripts` 遵循 Pi 1.2.0 的官方安装建议，跳过依赖安装脚本。后两项只关闭安装时的审计请求和赞助提示，不代表完成了安全审计。

## 源码怎样同步

这次沿用 Windows 已有的 GitHub 授权推送 `main`，然后通过 SSH 把 Git bundle 传到服务器。Git bundle 是包含提交历史的文件，服务器可以从中克隆或快进更新。

这样可以同步完整 Git 提交，而不用复制 Windows 的 GitHub 私钥到服务器。服务器 `origin` 仍记录正常的 GitHub 仓库地址；本轮没有配置或验证服务器直接访问私有 GitHub 仓库的认证，所以不要把设置了 `origin` 理解为服务器已经能直接 `git pull`。

当前流程为：Windows 修改并验证 → 提交并推送 GitHub `main` → SSH 传输 bundle → 服务器快进到相同提交。服务器若有未提交改动，应先处理这些改动，再同步，不能强行覆盖。

## 与参考项目有什么关系

参考项目的 `package.json` 明确列出 Pi `0.85.1` 的 `pi-coding-agent`、`pi-agent-core`、`pi-ai`。我们当前只直接依赖新版 `pi-coding-agent`；它会通过自己的依赖清单带入所需的底层组件。

这一步复现的是“把 Pi 作为项目依赖准备好”。参考项目的 `packages/agent-runtime/chat.ts` 等程序控制逻辑、后端和网页均不在本轮实现范围内。

2026-10-15 在上述服务器项目目录实际执行：

| 检查 | 实际结果 |
| --- | --- |
| `node --version` | `v24.16.0` |
| `npm --version` | `11.13.0` |
| `npm ci --ignore-scripts --no-audit --no-fund --fetch-timeout=30000 --fetch-retries=2` | 安装 118 个包，退出码 0 |

| 隔离环境中的 `npm run pi:help` | 正常显示参数和工具说明，退出码 0 |

本次版本和帮助检查清空了继承的环境变量，使用临时 Pi 配置目录并设置 `PI_OFFLINE=1`。帮助检查还传入 `--no-session --no-extensions --no-mcp --no-skills --no-prompt-templates --no-themes --no-context-files`，避免加载用户或项目已有资源。可按下面方式重现：

```bash
cd /home/hanwen/Project/project/siNRA-pi
smoke_dir=$(mktemp -d /tmp/sirna-pi-smoke.XXXXXX)
env -i PATH=/home/hanwen/.nvm/versions/node/v24.16.0/bin:/usr/bin:/bin \
  PI_CODING_AGENT_DIR="$smoke_dir/agent" PI_OFFLINE=1 \
  npm run pi:version
env -i PATH=/home/hanwen/.nvm/versions/node/v24.16.0/bin:/usr/bin:/bin \
  PI_CODING_AGENT_DIR="$smoke_dir/agent" PI_OFFLINE=1 \
  npm run pi:help -- --no-session --no-extensions --no-mcp \
  --no-skills --no-prompt-templates --no-themes --no-context-files
```

Pi 1.2.0 的帮助命令仍会创建内部运行对象，但在提交任务前退出。因此，这些检查证明安装和命令入口可用，不代表模型连接、真实工具调用、网页访问或会话恢复已验证。本轮没有提交模型任务。

安装时出现上游间接依赖 `node-domexception@1.0.0` 的弃用提示，安装及上述检查仍成功。首次生成锁文件时遇到一个请求长时间等待，单独验证下载地址可访问后，以 30 秒单请求超时重试成功；此超时仅用于本次命令，没有修改用户全局 npm 设置。
