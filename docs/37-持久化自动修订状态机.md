# 第12D步：持久化自动修订状态机与替代候选重新验证

## 这一阶段解决什么问题

第12C只把当前进程收到的“验证失败”通知交给 `ToolRepairService`。如果进程在修订期间重启，内存中的候选 Map/Set 会消失；替代候选提交后也没有稳定的自动验证入口。这与参考仓库的持久化自动化状态机不同。

第12D补上这一层：自动流程自己的运行记录保存到独立 SQLite，替代候选注册时在同一个事务中完成旧运行封存和新运行排队，新的候选拥有自己的验证请求 ID和独立验证结果。

## 状态如何变化

```text
queued
  ↓
validating
  ├─ passed:true  → approving（等待批准边界）
  └─ passed:false → repairing
                       ↓
                 awaiting_replacement
                       ↓ 新候选
旧运行 superseded；新运行 queued → validating
```

`approving` 在当前个人仓库中表示“验证已经通过，等待后续批准实现”，还不会自动激活工具。自动批准和发布仍然是后续阶段。

## 新增持久化存储

[tool-automation-store.mjs](../packages/capability-platform/tool-automation-store.mjs) 新建 `runtime/tool-automation/runs.sqlite`。每条记录保存：

- `proposalId`：当前候选；
- `sourceTaskId`：修订始终回到哪个任务；
- `curationId`：候选来自哪次 Curator 结果；
- `toolName` 和 `artifactSha256`：工具身份与不可变产物；
- `rootProposalId`、`previousProposalId`、`attempt`：修订谱系；
- `phase`、`lastError`、创建和更新时间。

`registerProposal()` 的事务逻辑与参考仓库一致：如果同一来源任务和工具名存在 `repairing` 或 `awaiting_replacement` 运行，就先把旧运行改为 `superseded`，再插入继承 `rootProposalId`、代数加一的新运行。插入失败时整个事务回滚，不会留下只有一半的谱系。

存储层最多允许三次替代代数，使用真实候选 ID、来源任务和产物摘要作为绑定；任意手写的状态或跨任务替代都会被拒绝。

## Builder 和 Repair 的通知

[tool-curation-build-service.mjs](../packages/extensions/tool-curation/tool-curation-build-service.mjs) 的 Builder 终态通知现在附带已登记候选的 `toolName`，供自动化存储记录身份。

[tool-repair-service.mjs](../packages/capability-platform/tool-repair-service.mjs) 增加了安全的 `sirna-tool-repair/v1` 终态通知。通知发生在修订 SQLite 已经写入 `awaiting_replacement` 或 `superseded` 之后；替代候选存在时只携带候选 ID、产物摘要和工具名，不携带修订提示、源代码、服务器路径或运行诊断。

## 协调器如何接回原流程

[tool-curation-coordinator.mjs](../packages/extensions/tool-curation/tool-curation-coordinator.mjs) 现在做四件事：

1. 自动 Builder 提交后先登记持久化自动化运行，再排队验证；
2. 验证失败时把运行设为 `repairing`，随后调用已有 `toolRepair.start()`；
3. 收到替代候选终态后调用 `registerProposal()`，旧记录和新记录在一个事务中切换；
4. 为替代候选生成新的确定性验证请求 ID，重新进入维护队列。

每次协调器 tick 都会读取 `listOpen()`。因此在当前进程 Map/Set 丢失后，新的协调器仍能：

- 从 `validating` 记录读取维护队列和失败报告；
- 从 `repairing/awaiting_replacement` 记录读取已有修订状态；
- 发现已经登记但通知丢失的替代候选；
- 继续排队替代候选的独立验证。

这类恢复只读取本自动化存储中已经登记的开放运行，不扫描所有历史候选，也不会把手动验证或手动修订误认成自动流程。

## 本阶段没有做什么

- 没有自动批准或发布工具；
- 验证通过后停在 `approving`，需要后续明确的批准边界；
- 没有让验证失败直接覆盖旧候选；
- 没有创建第二套修订谱系数据库，修订次数和父子关系仍由 `ToolRepairStore` 与 Tool Registry 负责；
- 自动验证和自动修订两个环境开关仍默认关闭。

本阶段的意义是把第12C的“当前进程回调”提升为参考仓库要求的“可重启、可恢复、可重新验证的持久化交接”。
