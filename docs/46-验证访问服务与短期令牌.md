# 第13C-F步：验证访问服务与短期令牌

## 这一步要解决什么问题

13C-E 已经能保存 retrieval receipt，并对冻结 artifact 做确定性检查，但 verifier 还没有一条受控的读取路径。若直接把整个 Bundle、消息正文或工具结果交给模型，会有三个问题：

1. 大段上下文会让 verifier 难以控制预算；
2. 任务消息和工具结果中可能包含不应该公开的内容；
3. 验证结束后，旧令牌若仍然有效，外部调用者就能继续读取该任务的证据。

本轮实现原仓库 Access Service 的离线核心：验证开始时生成一次性短期令牌，SQLite 只保存令牌的 SHA-256；Bundle 先返回脱敏元数据，正文和 artifact 通过分页接口读取；check 仍由后端读取不可变快照并写入 receipt。网络 search/fetch 继续关闭，避免把网络边界和访问授权混成一个步骤。

## 与原仓库的对应关系

| 原仓库正式实现 | 本学习版 | 本轮理解 |
| --- | --- | --- |
| `packages/extensions/goal/goal-verification-store.ts:begin/authorize` | `packages/extensions/goal/goal-verification-store.mjs:begin/authorize` | 运行状态绑定 token hash，终态清除 hash；比较时使用 timing-safe compare |
| `packages/extensions/goal/goal-verification-coordinator.ts` | `packages/extensions/goal/goal-verification-coordinator.mjs` | Bundle 冻结后生成 token，并以第二个参数传给 verifier |
| `packages/extensions/goal/goal-verification-access.ts:bundle` | `packages/extensions/goal/goal-verification-access.mjs:bundle` | 隐藏 message.content 和 tool resultPreview，仅返回长度、哈希、计数和访问提示 |
| `goal-verification-access.ts:message/artifact` | `goal-verification-access.mjs:message/artifact` | 按 offset/maxChars 分页；artifact 始终通过 `readArtifact()` 重新检查冻结快照哈希 |
| `goal-verification-access.ts:evidenceInventory` | `goal-verification-access.mjs:evidence` | 返回 message/artifact/tool/retrieval/check 的证据目录，不返回 retrieval 原文 |
| `goal-verification-access.ts:checkArtifact` | `goal-verification-access.mjs:check` → `goal-verification-evidence.mjs:checkArtifact` | 访问授权和确定性检查分层，检查结果继续保存为 receipt |
| `apps/api/extensions/goal-verification-api.ts` | `apps/api/router.mjs:/v1/goal-verifications/:id/{bundle,message,artifact,evidence,check}` | HTTP 仅接受 POST、路径 ID 与 body ID 必须一致，错误令牌返回 403 |

学习版只实现了原仓库的本地访问协议。原仓库后续还会把 search/fetch、attempt 和 Agent Compose verifier 工具接入；这些接口目前仍明确未开放。

## 逐文件解释

### `goal-verification-store.mjs`

`verification_runs` 新增 `access_token_sha256` 列。为了兼容 13C-A 至 13C-E 已经创建的 SQLite 文件，构造函数先查询 `PRAGMA table_info`，缺列时执行一次 `ALTER TABLE`，旧记录和旧 Bundle 不会被重写。

`issueAccessToken()` 使用 Node `crypto.randomBytes(32)` 生成 base64url 字符串。`begin(id, accessToken)` 把验证从 `pending` 切到 `running`，只写入 `sha256(accessToken)`；`record()` 返回的运行对象不会包含明文令牌。

`authorize(id, accessToken)` 只查询 `status='running'` 的记录，并把传入令牌哈希和数据库哈希做长度检查及 timing-safe 比较。`finish()` 与 `fail()` 都把哈希设为 `NULL`，所以通过、失败和错误状态都自动失去读取权限。

### `goal-verification-coordinator.mjs`

协调器在 Bundle 已经冻结、Goal 版本仍匹配之后才生成 token。这意味着 verifier 看到的 token 一定对应固定的 `verificationId` 和固定文件快照。它以 `verify(activeRun, accessToken)` 的第二个参数传给 verifier，保持原仓库 `AgentGoalVerifier.verify(run, accessToken, ...)` 的参数位置；当前 deterministic verifier 忽略该参数，但未来 Agent Compose prompt 可以用它调用访问接口。

### `goal-verification-access.mjs`

这是本轮的核心访问层。它不直接接收 HTTP request，而是接收已经解析过的 `{verificationId, accessToken}`，第一步统一调用 `store.authorize()`。

- `bundle()` 删除每条消息的正文，只留下 `contentCharacters`；删除工具回执的 `resultPreview`，只留下 `hasResultPreview`。
- `message()` 只允许读取属于当前 Bundle 的消息，返回 `offset`、`content`、`truncated`、`nextOffset`。单次 `maxChars` 最大 16,000。
- `artifact()` 只允许读取 Bundle 中登记的 artifact，调用 `GoalVerificationBundleBuilder.readArtifact()`，因此工作区之后改动不会改变验证输入。UTF-8 文件返回分页文字；二进制文件只返回元数据。
- `evidence()` 返回有限证据目录。retrieval 只返回来源 URL、类型和内容哈希，不把 `responseText` 暴露给目录接口；真正的来源正文仍等待后续受控 fetch/read 设计。

这里的 `message:<id>`、`artifact:<id>` 和 `tool:<eventId>` 是学习版当前阶段的稳定临时指针，尚未像原仓库 `EvidenceResolver` 那样写入独立 evidence-unit 表并生成随机持久 ID。因此它能验证“访问边界和分页”已经接通，但还不能宣称与原仓库的完整证据协议等价；后续接 resolver 时会把这些临时指针替换为后端生成、可去重、可重放的证据记录。
- `check()` 复用 13C-E 的 `checkArtifact()`，所以检查结果仍绑定 artifact SHA-256，并写入 `verification_checks`。

`summary()` 只给网页列表和详情返回 ID、Goal 版本、状态、Bundle 哈希、artifact/tool 数量和时间，不把整个 Bundle 或 evaluation 原文放进公共列表。

### `goal-verification-runtime.mjs` 与 `apps/api/router.mjs`

runtime 创建 `access`，并把只读 `public` 摘要接口和 token-scoped `access` 同时返回。API 新增五个 POST 路径：

```text
POST /v1/goal-verifications/:verificationId/bundle
POST /v1/goal-verifications/:verificationId/message
POST /v1/goal-verifications/:verificationId/artifact
POST /v1/goal-verifications/:verificationId/evidence
POST /v1/goal-verifications/:verificationId/check
```

请求体必须含 `accessToken`。`message` 还需要 `messageId`，`artifact` 和 `check` 需要 `artifactId`，`check` 需要受支持的 operation。访问接口拒绝查询参数和 GET；路径中的 verificationId 与 body 中若有的同名字段不一致时拒绝。这个路由只做 HTTP 编排，真正的身份、Bundle 归属和文件哈希检查仍在包内完成。

## 一次读取如何流动

```text
Agent Compose verifier
        │  verificationId + accessToken
        ▼
POST /v1/goal-verifications/:id/bundle
        │  store.authorize(status=running, hash(token))
        ▼
脱敏 Bundle（正文和 resultPreview 被隐藏）
        │
        ├─ POST message/artifact：分页读取，artifact 重算冻结文件哈希
        ├─ POST evidence：读取安全目录，不返回 retrieval responseText
        └─ POST check：不可变快照 → 确定性检查 → SQLite receipt
        │
finish/fail
        ▼
access_token_sha256 = NULL，旧 token 失效
```

网页公共 GET 仍只展示 `summary()`；网页或普通用户不能凭任务 ID 直接拿到消息正文。后续真正的 Agent Compose verifier 会在自己的 prompt 中收到 token，并通过这些接口逐步取证。

## 验收结果

先按测试驱动流程运行不存在模块的红灯测试，确认访问层缺失时失败；实现后运行：

```text
node --test tests/goal-verification-access.test.mjs \
  tests/goal-verification-evidence.test.mjs \
  tests/goal-verification-coordinator.test.mjs \
  tests/goal-verification-bundle.test.mjs \
  tests/goal-api.test.mjs
```

定向结果为 24 项通过。新增测试覆盖令牌错误、Bundle 脱敏、消息/artifact 分页、foreign verification 拒绝、确定性 check receipt、终态令牌失效，以及 HTTP POST-only 和路径身份绑定。

随后运行 `npm test`：1564 项测试，1548 项通过，16 项平台相关跳过，0 项失败。直接运行 `node --test` 会递归扫描 `runtime/` 下的历史隔离副本，其中部分副本故意缺少当前源文件；项目正式测试命令是 `npm test`，只运行 `tests/*.test.mjs`。

## 当前边界与下一步

这一轮证明的是本地访问协议和令牌生命周期，不证明真实 Agent Compose 能正确规划读取顺序，也不证明外部文献内容真实。当前还没有：

1. search/fetch 的真实受控网络请求、重定向和响应解析；
2. `attempt` 读取和 verifier retry feedback；
3. Agent Compose verifier 的工具 schema、prompt 和真实模型调用；
4. verifier 使用证据后对 Goal 的真实 pass/fail 结果。

下一步会先把 `controlled search/fetch` 作为独立网络边界接入，继续沿用 allowlist、大小上限、重定向限制和 receipt 哈希；之后再接 Agent Compose 独立 verifier。deterministic fake verifier 会保留，作为无网络、无模型回归夹具。
