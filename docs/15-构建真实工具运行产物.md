# 第10B步：把工具代码保存成真正可以运行的镜像

## 一、从上一轮的缺项开始

第10A步检查的是一份提案有没有把工具名称、源码、输入、预期输出、依赖和权限说清楚。教学草稿在正式提交要求下缺少`runtimeArtifact`，原因是还没有一个真实环境承载这段代码。

本轮补的是运行产物：准备专用构建容器，把候选源码写进去，检查并运行，保存为镜像，然后从这个镜像启动新的运行容器。我们既保存“想运行什么”的提案，也获得“实际运行哪个成品”的标识。

这里的镜像可以理解为容器启动时使用的一份文件系统和配置快照。Docker返回的`sha256:...`是本机镜像的内容标识（ImageID），不是可以随便填写的编号，也不是已经上传到镜像网站的下载地址。

## 二、原仓库怎么做，本轮做到哪一段

参考应用965c53f、checkout67d2754的主要文件：

| 参考文件 | 职责 |
| --- | --- |
| packages/domain/sirna-tools/sirna-tools.ts | 向Agent提供create_tool_build_session、write_tool_build_file、run_tool_build_command、finalize_tool_build、cancel_tool_build_session |
| packages/capability-platform/tool-runtime-client.ts | 把构建工具的请求送到工具运行控制器 |
| packages/capability-platform/tool-runtime-controller.ts | 管理构建容器，完成commit，按镜像摘要启动运行容器 |
| packages/capability-platform/docker-engine-client.ts | 与Docker Engine通信，执行具体容器操作 |
| packages/capability-platform/tool-lifecycle.ts | 后续独立验证、登记状态与版本流程 |

工具构建控制器和Agent Compose各有职责：Agent Compose管理网页任务里的Pi；工具控制器管理被封装的工具代码及其运行环境。不能把“有了Pi任务容器”当成“已经有了新工具的可发布运行产物”。

本轮先实现工具控制器的构建/执行内核，由可信宿主CLI驱动。尚未增加HTTP构建服务和MCP构建工具，因此网页里的Agent没有获得Docker控制权限。后续可以把相应接口接到这层内核，不必将容器操作塞进网页路由或序列计算函数。

原finalize实际上只探测入口存在，再stop→commit，并不强制已经冒烟测试；真正完整门禁在独立验证器。本学习步骤增加“构建前冒烟、成品案例复测”，便于看到真实证据，但仍不能称完整验证器已完成。

## 三、docker-engine-client.mjs：把请求交给Docker

新增`packages/capability-platform/docker-engine-client.mjs`。Docker并不只接受终端命令，也提供HTTP形式的程序接口。本模块使用Node内置HTTP，通过指定Unix socket调用这些接口。

本项目的socket是`runtime/docker/run/docker.sock`。构造客户端时必须明确传入它，不能回落到共享`/var/run/docker.sock`，也不从宿主环境变量自动挑选其他Docker。

主要动作包括createContainer、startContainer、exec、stopContainer、commitContainer，以及执行阶段的waitContainer和containerLogs。调用方传入JSON和命令参数数组，宿主机不把候选源码拼成shell命令执行。

Docker的非TTY输出把stdout与stderr分成带帧头的数据块。本模块先检查帧头和长度，再还原两种输出；损坏或截断不能当成正常文本。HTTP失败、超时、响应过大、未结束的exec和非法返回值都需要报告失败。创建和commit没有自动重试，避免响应不确定时重复生成资源。

## 四、tool-build-service.mjs：编排一次构建

新增`packages/capability-platform/tool-build-service.mjs`，主要入口为`buildToolArtifact()`。

本阶段范围明确：只支持Node、自包含代码、无第三方依赖、无外部访问、exact重复性，且最多10个功能案例。先检查草稿，再检查是否属于已支持范围。声明Python、联网或软件依赖时应明确拒绝，而不是悄悄忽略这些要求。

源码沿用合同的200000字节上限，上传时分块传入固定写入程序，避免超过Linux单个命令参数的长度上限。每个业务输入的JSON最多65536字节，所有案例在创建容器前一起检查，避免构建到一半才发现后续输入过大。

构建使用之前已经验证过的Pi1.2.0基础镜像的固定ImageID；这次不安装Pi、不启动Pi、也不请求大模型。重用它是因为其中已有Node运行环境，固定摘要还能防止同名标签指向不同内容。该基础镜像较大，后续可以讨论更小的专用工具底座。

执行过程如下：

1. 创建专用构建容器，设置唯一构建会话编号及本项目归属标签。
2. 将提案的候选`script`写入`/opt/tool/main.mjs`；`baseline`不写入候选镜像。
3. 运行Node语法检查，重新读取源码计算SHA-256，核对与提交源码一致。
4. 用业务输入外面包一层`sirna-approved-tool-call/v1`信封，通过stdin送给候选代码；以非root用户实际运行冒烟案例。
5. 冒烟输出满足约定后停止构建容器，调用Docker commit保存镜像。
6. 在镜像配置和标签中记录命令、非root用户、源码哈希、基础镜像、构建会话及时间；返回兼容原合同的六字段artifact。
7. 删除本次构建容器，再从成品ImageID为每个功能案例启动新的受限容器并复测。

每项操作都会留下事件。任何阶段失败，都不能把结果包装成成功构建；清理也需要确认，只针对本次创建且归属核对成功的容器。

语法错误和冒烟失败会先保存退出码、stdout、stderr与`passed:false`，再抛错和清理。否则容器虽然清理干净了，学习者却看不到究竟哪一行出错。`baseline`继续作为后续比较材料保存在提案中，本轮既不执行它，也不把候选通过两个案例解释成“超过基线”。

返回的`runtimeArtifact`沿用原仓库六个字段：

| 字段 | 回答的问题 |
| --- | --- |
| protocolVersion | 这份运行产物说明遵守哪个格式？ |
| imageDigest | 实际执行的是哪个不可变的本地镜像内容？ |
| command | 容器中启动哪个程序？本步固定为`/usr/bin/node /opt/tool/main.mjs`。 |
| platform | 该镜像面向哪个系统和处理器架构？本次为`linux/amd64`。 |
| createdAt | 这次构建何时保存？ |
| buildSessionId | 应到哪个构建记录目录追查过程？ |

## 五、成品运行为什么需要新容器

`executeToolArtifact()`按artifact里的ImageID创建新容器。它核对镜像内的命令、用户、平台、构建会话及来源标签，防止调用时任意替换命令或把其他镜像冒充本次成品。

每个案例都有新的运行容器，因此不能依赖前一次运行留下的临时文件。运行使用65534:65534用户，只读根文件系统，仅提供有限的`/tmp`临时空间；关闭网络，不挂载项目目录、模型凭据或Docker socket。

构建和运行均声明1GiB内存、64个进程的上限，去除Linux capabilities并设置no-new-privileges。当前rootless环境不支持CPU配额，因此没有CPU限制；这些设置也不代表任意敌对代码都已获得充分安全证明。本轮命令只用于我们审阅过的教学代码，尚未向Agent开放。

返回的记录包含真实退出码、stdout、stderr、JSON解析及案例匹配结果。不会为了满足第10A步完整验证记录格式而编造`filesDigest`。本轮未执行完整静态规则、双次冒烟重复性门禁、基线净增益比较、登记审批，因此成功结果仍明确未verified、未registered、未activated。

## 六、命令入口与保存文件

新增`scripts/build-tool-artifact.mjs`，以及负责受限读取和证据保存的`scripts/lib/tool-build-files.mjs`。命令限定在指定Linux项目目录由hanwen执行，不能使用sudo或通过环境变量切换Docker。

在已有Node24环境中运行：

```sh
cd /home/hanwen/Project/project/siNRA-pi
npm run build:tool -- examples/04-tool-contract/proposal.draft.json
```

这条命令会真实执行提案代码并创建镜像，与上一轮只读预检不同。每次使用新的构建编号，不覆盖原始草稿，也不覆盖先前的证据。

私有`runtime/tool-builds/<构建编号>/`中包含：

| 文件 | 内容 |
| --- | --- |
| source-proposal.json | 本次提交材料的快照 |
| request.json | 请求时间、源码哈希、构建编号 |
| events.jsonl | 每步事件、容器标识和检查记录 |
| result.json | 成功构建及成品运行的结果 |
| preflight.json | 填入真实artifact后的完整字段预检 |
| proposal.json | 加入真实runtimeArtifact的提案副本；只在成功后生成 |
| failure.json | 失败时的诊断；成功时不生成 |

这些记录和真实运行产物不进入Git。输出目录和文件只允许当前用户访问；源码读取有大小限制，拒绝链接、目录和无效UTF-8/JSON。证据文件不覆盖已有内容。

程序正常失败会尝试精确清理。主机崩溃或SIGKILL可能留下构建容器；本步尚无后台TTL/重启恢复服务。应依据事件里的容器ID和归属标签核查，不能全局清理Docker或删除旧任务容器。镜像作为本轮产物保留，即使后续检查失败也保留诊断标识，不擅自清空镜像缓存。
