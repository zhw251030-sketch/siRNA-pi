# 13A Goal 核心闭环

## 目标

参考原仓库 M6 的 Goal 边界，在个人版 JavaScript 服务中实现一个可持久化、可恢复、有限自动推进的任务目标。先实现 Goal 的状态与调度，不引入独立 verifier、Memory、Data Pool 或 Black-box。

## 参考实现

- `packages/extensions/goal/goal-plan.ts`: 目标拆分为有界工作项，完成前不能直接结束。
- `packages/extensions/goal/goal-store.ts`: SQLite 持久化、revision、lease、自动回合预算与状态迁移。
- `packages/extensions/goal/goal-coordinator.ts`: 空闲任务领取 lease，向 Pi 发续作提示，按结果更新预算和失败退避。
- `apps/api/extensions/goal-api.ts`: GET/POST/PATCH/DELETE `/v1/tasks/:taskId/goal`。
- `apps/api/router.ts`: 将 Goal 作为任务消息和任务列表的一部分暴露。
- `packages/extensions/goal/goal-tools.ts`: `get_goal/create_goal/update_goal` 工具合同。

## 个人版设计约束

- 使用 ES modules；Goal 数据单独存放在 `runtime/goal/goals.sqlite`，避免修改已冻结的任务数据库 schema。
- 目标创建必须绑定已存在任务；停止任务不能创建 Goal。
- 自动回合调用现有 `TaskMessageService.start`，不绕过任务消息持久化和 Agent Compose。
- 只允许后端持久状态推进完成；若还有必需工作项，`complete` 拒绝。
- 默认自动协调器关闭，通过环境变量 `SIRNA_GOAL_COORDINATOR=1` 开启，避免启动已有服务时改变行为。
- 先支持基础 `get_goal/create_goal/update_goal`，工具接线沿用现有 Agent tools server 的 task-scoped 设计；独立 verifier 留在下一阶段。

## 实施任务

1. 写 Goal plan/parser 与 GoalStore，覆盖 SQLite schema、状态迁移、revision、lease、预算和重启恢复。
2. 写 GoalCoordinator，接入 TaskMessageService，保证不与用户回合并发，记录 requestId 和终态。
3. 写 Goal API 与路由，补充任务消息/任务列表中的 goal 字段。
4. 写 task-scoped Goal tools，使 Pi 可读取目标、创建目标、提交进度/阻塞/完成申请。
5. 在 bootstrap/lifecycle 中装配、启动、停止并关闭 Goal 服务。
6. 先写单元/集成测试，再运行 focused、串行全量、diff 检查。
7. 写逐文件教学文档，更新学习路线与 README，说明与原仓库的对应关系、当前限制和下一阶段 verifier。

## 验收

- 同一 task 创建 Goal 后可 GET，重复创建按原仓库语义拒绝未完成 Goal。
- 未完成必需项时完成申请被拒绝；progress 需要合法工作项和 revision。
- pause/resume、blocked、budget_limited、lease recovery 可持久化并可恢复。
- coordinator 只有任务空闲且无用户输入时自动发送续作，超过预算停止。
- HTTP 和工具输入严格校验，不能越过 taskId 或修改其他任务。
- 现有全量测试保持通过。
