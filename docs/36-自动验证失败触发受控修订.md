# 第12C步：自动验证失败触发受控修订

第12B步已经能把本进程自动 Builder 的 `submitted` 候选放进独立验证队列。本步继续复现参考仓库中的下一段：验证作业完成且明确发现候选不通过时，把可信失败报告交给已经存在的修订服务，由原任务执行一轮受控修订。

本步的“自动”只表示自动发起一轮修订请求。修订候选仍然必须重新登记、重新独立验证，并由人批准。替代候选不会因为修订消息结束就被当作成功，也不会被本轮自动再次验证或自动发布。

## 链路变化

```text
自动 Builder submitted
  → 自动验证队列
  → Docker 独立验证
  → 持久报告 passed=false
  →（SIRNA_AUTOMATIC_REPAIR=1时）已有 toolRepair.start()
  → 原任务一轮受控修订
  → awaiting_replacement
  → 新候选 submitted（仍待验证/批准）
```

两个开关分别控制两个动作：`SIRNA_AUTOMATIC_VALIDATION=1` 负责入队验证，`SIRNA_AUTOMATIC_REPAIR=1` 负责失败后发起修订。两者默认都是关闭状态。打开修订开关而没有自动验证来源时，也不会扫描历史候选或把人工验证误认为自动验证。

## 为什么不重新实现修订系统

个人仓库已经在第10N、10O步实现了可信修订底座：

- `tool-repair-store.mjs` 将修订票据写入独立 `repairs.sqlite`；
- `tool-repair-service.mjs` 检查失败状态、可信来源任务、报告摘要、任务空闲和三代预算；
- `tool-repair-contract.mjs` 冻结工具名、运行时、依赖、权限、测试、基线、净收益门槛和正式父版本；
- `tool-proposal-source.mjs` 检查 `previousProposalId`、`rootProposalId`、`attempt` 和同一来源任务；
- 新候选登记后，旧修订票据变为 `superseded`；服务重启会把未确认的 `dispatching/running` 标为 `interrupted`，不自动重发。

因此本轮只增加观察桥，避免把安全的来源绑定和谱系规则复制成第二套实现。

## 逐文件理解

### `tool-maintenance-worker.mjs`

维护 worker 增加可选 `onSettled`。它在 `jobs.sqlite` 已写入 `succeeded/failed` 后发送小型通知，字段包括 `jobId`、`proposalId`、作业状态、`passed`、`validationId` 和 artifact SHA。若业务验证失败，worker 尝试从只读失败反馈中补充 `reportSha256`；报告损坏时不传递修订证据。

通知不包含 Docker 容器、路径、stdout、stderr 或异常文本。通知失败不会改变已经保存的维护作业。未知 Docker 清理、容器身份不确定或队列重启中断都只产生失败/中断通知，不会触发自动修订。

### `tool-curation-coordinator.mjs`

协调器在自动验证入队时记录 proposal 与本轮 Curator/Builder 来源的内存绑定。`observeMaintenance()` 只处理这个绑定中的作业，并要求：

1. 作业是正常完成的 `succeeded`；
2. `passed` 明确为 `false`；
3. artifact SHA 与入队时相同；
4. `validationId` 和 `reportSha256` 格式正确；
5. 第二个自动修订开关已打开。

通过后只调用 `toolRepair.start(proposalId,{validationId,reportSha256})`。任务忙、报告不可读、维护服务停止、修订额度耗尽或已有修订票据都会安全拒绝。重复维护通知不会创建第二个修订请求。

协调器不读取历史 `submitted` 候选，也不在重启后猜测某个作业属于自动流程。它只保存本进程自动验证的来源映射；这与原仓库的持久 automation run 相比更保守，但能先验证来源、报告和任务状态的正确连接。

### `apps/api/bootstrap.mjs`

维护 worker 通过延迟闭包通知协调器，避免初始化顺序造成空引用。协调器接收已有 `toolRepair` 服务，并读取 `SIRNA_AUTOMATIC_REPAIR`。因此网页、HTTP 和已有显式修订 API 不变，自动能力只是后台的额外观察路径。

## 与参考仓库的差异

参考仓库会把验证失败写入持久 `ToolAutomationStore`，进入 `repairing`，等待来源任务空闲，再进入 `awaiting_replacement`，并沿同一任务和工具名继承替代候选谱系。本学习仓库复用了已有的 `ToolRepairStore` 和 `ToolRepairService`，先实现其中的“失败报告到修订消息”连接；持久自动化运行阶段字段、替代候选自动注册后的继续推进、自动验证替代候选和自动批准仍未实现。

## 验收重点

本轮测试保护以下边界：维护终态通知发生在持久写入之后；通过验证、未知结果和基础设施失败不会修订；默认修订关闭时无副作用；明确失败只调用一次现有修订入口；报告摘要或产物摘要错配时不派发。完整修订底座的来源、冻结合同、三代上限、重启中断和替代候选 supersede 继续由原有 106 项测试保护。

下一阶段是把 `awaiting_replacement` 的新候选结果接回验证状态机，并决定是否需要一个持久的 automation run 投影。自动批准、Goal 限制、Memory/Data Pool、Workbench 和 Black-box 仍未完成。
