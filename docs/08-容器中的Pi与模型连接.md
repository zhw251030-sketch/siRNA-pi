# 第 5 步 C：让任务容器中的 Pi 真正调用模型

日期：2026-10-20。承接第 5 步 B 的 Agent Compose 命令工作区；容器内真实文件任务、同会话续问和释放检查均已通过。

## 1. 上一步有了房间，这一步让 Agent 在房间里工作

上一步已经证明：Agent Compose 能创建一个 Docker 容器，让固定命令在里面执行，把文件保存到服务器，再释放容器。但是命令是我们预先写好的，既没有启动个人使用的 Pi 1.2.0，也没有让模型决定调用工具。

这一步要连通的流程是：

```text
学习用验收脚本
  → Agent Compose 创建并管理任务容器
  → 容器内的官方 PiRunner 启动 Pi 1.2.0
  → Pi 把问题和 read/write 工具说明发给控制服务的模型转接接口
  → 控制服务携带 MiniMax 密钥请求国内 MiniMax-M3
  → 模型返回工具调用要求
  → 容器内 Pi 执行 read/write，结果再交给模型
  → 写出真实文件，保存会话，报告运行结束
```

这里没有重新实现 Pi 的思考或工具循环。Pi 仍提供这些能力；我们增加的是安装、配置、连接和验证。模型决定是否调用 read/write 以及调用参数，Pi 执行实际文件操作，Agent Compose 管理环境和运行。验收程序最后独立检查真实结果。

当前网页仍通过 LocalPiRuntime 调用服务器上的 SDK。先验证容器内的这条链路，可以在下一步把网页执行器切换过来时，更容易区分问题出在网页、执行平台还是模型连接。

## 2. 两个容器，各自做不同的事

| 对象 | 持续时间 | 主要工作 | 能看到什么 |
| --- | --- | --- | --- |
| controller，控制服务容器 | 常驻 | 接收任务、创建 guest、记录状态、转接模型请求 | 项目 Docker socket、管理数据、单个密钥文件、公共配置 |
| guest，任务容器 | 一个任务环境需要多久就保留多久 | 运行 Pi、执行工具、读写任务文件 | 该 sandbox 的工作区、会话和运行状态；模型转接令牌 |

控制服务不是大模型，也不是 Pi 本身。它安排 Pi 在哪里运行。guest 不是网页，它是实际干活的环境。

Docker 镜像可以理解为“安装好程序的环境模板”；容器是从模板启动的具体运行实例。多个任务可以使用同一份镜像，但各有自己的工作目录与会话。镜像版本一致不等于任务数据共用。

## 3. 制作个人 guest：Dockerfile 与锁定依赖

文件：`containers/agent-compose-guest/Dockerfile`。

原仓库也从官方 Agent Compose guest 出发，再安装指定版本的 Pi 和专业软件。我们沿用相同做法，保留官方 guest 内的运行协议和 `agent-compose-runtime`，这轮只装 Pi，不提前加入 RNA 工具与 MCP。

`FROM ...@sha256:...` 固定官方底座。官方 guest 当前内置 Pi 0.82.1，参考项目另装 Pi 0.85.1；个人项目明确使用 1.2.0，因此不能把底座里已有的 Pi 直接当作个人目标版本。

`COPY package.json package-lock.json ./` 与 `npm ci` 将个人项目锁定的依赖装入 `/opt/sirna-pi`。只写 `npm install -g ...@1.2.0` 虽然固定顶层 Pi 版本，但它的子依赖仍可能变化；沿用 lockfile 能确定这一层依赖。

`RUN test ... = 1.2.0` 在构建时实际启动版本命令，版本不对就让构建失败。最后恢复 `/workspace` 工作目录，继承上游入口与保持容器运行的命令。

`.dockerignore` 使用允许清单，只发送 package 文件、guest Dockerfile、包装脚本及无密钥设置。服务器的 `docs/auth.json`、`runtime/`、已有会话都不送入构建上下文，更不会通过 `COPY .` 进入镜像。

`scripts/build-project-guest.sh` 使用项目专用 Docker 客户端构建 `sirna-pi-guest:pi1.2.0`。这个 tag 是本项目的本地镜像名称，验收另记录实际 ImageID。构建不安装系统软件，也不使用共享 Docker socket。

## 4. 启动 Pi：为什么多了一个小包装器

文件：`containers/agent-compose-guest/pi.sh`、`config/pi/compose-settings.json`。

Agent Compose 原本就会执行 `pi --mode json ...`，并传入模型名称、会话目录以及继续对话时的会话编号。包装器位于 `/usr/local/bin/pi`，接住这个启动请求，然后执行我们安装的 Pi 1.2.0。

包装器主要做三件事：

1. 确认 Pi 的状态目录是官方 guest 使用的 `/root/.pi/agent`。
2. 将个人运行设置复制到这个实际挂载的目录。只把设置放进镜像中的 `/root/.pi` 不够，因为启动容器时，持久化挂载会覆盖镜像中的同名目录。
3. 增加 read/write、关闭 MCP 和自动扩展等参数，再通过 `exec` 启动真正的 Pi。上游传入的参数通过 `"$@"` 保留。

不要加 `--no-session`：这会破坏后续多轮对话需要的会话保存。也不要用个人旧 `models.json` 覆盖这里的模型配置：它应由 Agent Compose 根据本次 sandbox 生成，里面指向控制服务的转接接口。

设置关闭自动重试和自动压缩，是本阶段的兼容措施。Pi 1.2.0 新增了更细的结束和重试语义；旧 PiRunner 会记住首次错误，可能把后来重试成功的任务仍判为失败。关闭这些行为可以先验证正常调用链；不能据此声称全部新版边界都已兼容。

read/write 是工具允许清单，不是“只能访问 `/workspace`”的操作系统权限策略。容器提供独立文件系统和明确的宿主挂载范围；Pi 原生文件工具仍可能访问 guest 内可访问的其他路径。因此这轮验收还检查实际调用是否只发生在样例输入和输出目录，后续若要严格限制 guest 内路径，需要单独实现并验证。

## 5. 模型配置：为什么两个配置文件都出现 MiniMax

文件：`agent-compose.yml`、`config/agent-compose-models.json`。

`agent-compose.yml` 的 `designer` 描述“这类 Agent 用什么环境和模型”：

```yaml
provider: pi
model: minimax-cn/MiniMax-M3
image: sirna-pi-guest:pi1.2.0
```

这里的 `provider: pi` 指执行 Agent 的程序类型；`minimax-cn` 则是模型服务的配置编号。这两个 provider 不在同一层，不能混为一谈。

`config/agent-compose-models.json` 描述“模型请求实际发到哪里、采用什么协议、从哪里取得认证”。它使用已有 SDK 成功使用的国内 `api.minimax.cn` 域名，采用 Anthropic Messages 兼容协议。协议名称说明请求格式，不代表模型变成了 Claude。

`apiKey: "$MINIMAX_CN_API_KEY"` 是环境变量引用，代码仓库里没有真实密钥。`maxOutputTokens: 4096` 会由控制服务强制应用为每次模型响应的输出上限；它不是整个任务总 token 或费用上限。

控制服务的上游地址含 `/anthropic/v1`；guest 生成的 facade 地址不手动附加 `/v1`，因为 Pi 的 Anthropic SDK 会追加版本和 messages 路径。照搬两个相同 URL 反而可能重复 `/v1`。

## 6. 谁拿密钥，谁拿临时通行证

文件：`containers/agent-compose/entrypoint.py`、`compose.yml`。

原仓库把 MiniMax 密钥通过环境变量交给控制服务。本项目沿用控制端集中连接模型的职责，但继续使用用户已经指定的 `docs/auth.json`，避免再复制一份密钥配置。

Docker Compose 只读挂载这一文件到 controller 的 `/run/secrets/minimax-api-key`。Python 启动程序检查它是当前用户拥有、0600 权限、非链接的普通文件，内容是一行非空 ASCII 文本，然后把内容放进即将启动的 daemon 进程环境。出错只给一般提示，不回显内容。使用 Python 是因为官方 controller 已有该解释器，不需要给控制镜像额外安装 Node。

`execve` 用真正的 daemon 替换 Python 进程；外层继续保留官方 tini，以处理容器信号和子进程。真实 key 不出现在 Docker 的 `Config.Env` 或命令参数里。

但真实 key 会被官方 Agent Compose 解析后保存到 `/data/data.db`。因此 `runtime/agent-compose/data` 整个目录都是敏感控制状态，不能公开或当成普通产物同步。当前外层私有权限和 guest 只挂自身 sandbox 子目录的安排仍需保持。

guest 得到的是 Agent Compose 发放的 facade 令牌，通过 `http://agent-compose:7410` 请求控制服务，再由控制服务请求 MiniMax。该令牌绑定 sandbox、provider 和协议；它默认并非定时自动过期，也不严格锁定单一模型。停止 sandbox 后代理拒绝它，释放/移除环境会撤销它。

独立的管理 token 仍保存在 `runtime/agent-compose/control.env`，用于管理接口认证，不能和模型 key 或 facade token 混淆。controller 的 7410 端口仍只绑定服务器 loopback；guest 使用项目私有 Docker 网络访问它。

## 7. 如何证明模型真的做了文件任务

文件：`scripts/verify-agent-compose-model.mjs`、`scripts/lib/verify-compose-file-task.mjs`。

集成脚本先 `up` 登记配置，再像原仓库 `startWorkspace()` 一样，通过固定命令创建 input/work/output/tool-drafts 四个目录。随后等这次初始化真正 succeeded，取得 sandboxId 和真实 workspace_path。`--detach` 返回只表示接受请求，不能据此报成功。

脚本在这个新工作区放入 `value` 列为 10、20、30、40 的 CSV，再把要求交给同一个 sandbox 中的 Pi：读输入、计算、写 JSON、重新读输出确认。结果文件必须原先不存在，避免误用旧产物。

验收器同时看两份东西：

- Pi 原生 JSONL 会话：模型有没有真的发出 read/write 调用，每个调用是否有匹配的成功工具结果，模型和结束状态是否正确。
- 服务器磁盘中的输入和输出：独立算出 count=4、sum=100、mean=25，比较文件内容并检查输入没有被改写。

模型说“我已经保存”不能替代这两项证据。也不把 assistant 消息数量直接称为 HTTP API 调用次数。

第二轮只问第一轮要求记住的随机口令。验收要求仍为同一个 Pi 会话编号、原 JSONL 保留并继续追加、回答记得口令且没有工具调用。这比只看到同一个 sandboxId 更强：同一个容器也可能启动全新的空对话，所以还要验证真正的上下文延续。

结束时只停止本次新 sandbox，验证状态 released、guest 容器已移除、输出仍在。保留日志和会话便于学习，不做全局 prune 或删除历史任务。

## 8. 与原仓库对应，哪些地方还没到

| 本轮文件或操作 | 参考实现 | 一致的职责与本轮边界 |
| --- | --- | --- |
| guest Dockerfile | `containers/agent-compose-guest/Dockerfile` | 从官方 guest 增加固定 Pi；暂不安装专业软件/MCP补丁 |
| `compose.yml` | 原仓库同名文件的 agent-compose 服务 | 常驻控制服务、模型配置、数据目录；个人版使用项目 rootless socket 和少量单文件挂载 |
| `agent-compose.yml` | 原仓库 designer Agent 定义 | 选择 Pi、模型、镜像；暂不搬入其他 Agent、提示词或专业能力 |
| 公共模型目录 | `config/agent-compose-models.json` | 控制端解析模型服务配置；个人版沿用已验证的国内域名 |
| 初始化、复用 sandbox | `packages/agent-runtime/executor.ts` | up、run --command 初始化、保存 sandboxId 后继续运行 |
| 真实模型运行 | `agent-compose-runtime.ts` / `rpc.ts` | 当前 CLI 与正式网页 RPC 共用底层 PiRunner；本轮未接网页 RPC 和事件流 |

本轮不能解释成网页已经切到容器，也不是完成全部“封装 Agent”。下一步才是在现有网页运行时边界中加入 Agent Compose 实现，把任务、sandbox、会话与结构化事件接起来。工具封装、专业 siRNA 软件、人工审核和自进化仍是后面的学习内容。
