日期：2026-10-15。本文说明本轮代码及其学习目的。实际运行结论单列在最后的验证区，区分已验证范围与后续工作。

用户已明确：学习目标是逐步重建原仓库当前正式架构，包括 Agent Compose 和独立任务容器。因此，这一步同时调整网页流程、后端分工和记录方式，为下一步接入正式执行器做好接口准备。当前实际执行器仍为 `local-pi`，它在服务器 Node.js 进程中调用 Pi SDK。

## 1. 从“按一次按钮”变成“在一个任务里工作”

第 3 步做的是最小闭环：输入要求 → 执行 → 显示最终答案。再次发送，就建立一份全新会话与目录。它适合看清网页怎样调用 Pi，但与原仓库正式工作方式存在差别。

原仓库围绕“任务”组织工作。你先创建一个任务，然后在里面提出要求、继续追问、查看文件、重新打开历史。任务可以包含许多轮对话。

例如：

1. 新建一个任务，要求读取 `numbers.csv`，计算数量、总和和平均值。
2. 在同一个任务里追问：“刚才算出的平均值是多少？解释一下计算过程。”
3. 刷新网页后，还能看见前两轮对话及工具操作。
4. 新建另一个任务，开始独立的练习，不默认继承第一个任务的对话与文件。

这里的“继续记得”来自程序保存并重新提供上下文。模型权重没有被训练或修改，也没有因此获得自进化能力。

| 要解决的问题 | 第 3 步 | 本轮代码 |
| --- | --- | --- |
| 怎样开始 | 直接发送要求 | 先建任务，再发消息 |
| 第二次发送属于哪里 | 全新任务 | 当前选中的任务 |
| 等待时看到什么 | 等待提示，最后一次返回 | 执行说明、工具状态等事件陆续返回 |
| 刷新后从哪里恢复 | 没有网页历史读取 | 从 SQLite 读取任务、消息和事件 |
| 模型怎样继续前文 | 每次只有本轮上下文 | 打开同一个 Pi 会话文件继续 |
| 后端代码怎样分工 | `src/` 中少量函数 | 按原仓库分成 API、Task Core、Agent Runtime |
| 实际执行环境 | 服务器内直接调用 SDK | 仍为 SDK 过渡执行器，容器阶段尚未完成 |

## 3. 点击“新建设计任务”时，做了什么

网页的 `public/app.js` 向 `POST /v1/tasks` 发送一个 `requestId`。它是本次创建请求的编号，用来识别“同一个请求被再次发送”的情况。

`router.mjs` 接住请求，将它交给 `TaskMessageService.createTask()`。这个函数依次：

1. 检查该请求是否已经创建过任务；若已创建，返回原任务。
2. 调用执行器的 `create()`，准备一个执行会话。
3. 调用 `TaskStore.createTask()`，保存网页任务及它对应的执行会话编号。
4. 把任务记录交回网页，加入左侧任务列表。

当前 `LocalPiRuntime.create()` 会建立任务目录、复制四个数的样例，并保存执行会话元数据。它不会调用模型，也不会预先生成统计答案。

接口返回的 `memory` 和 `dataPool` 保留原仓库的结构，本轮均为空。这只是接口对齐，不表示已经实现记忆文件、数据资产或相关专业功能。

页面沿用原仓库“新建设计任务”的入口名称。现阶段它仍是基础文件练习任务，尚不能因为这个名称就当成已具备 siRNA 设计能力。

## 4. 点击“发送”时，做了什么

现在消息发往具体任务：

```javascript
fetch(`/v1/tasks/${taskId}/messages`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ message, requestId }),
});
```

这是说明请求的简化片段；实际代码还会编码地址中的任务编号。

`TaskMessageService.start()` 检查消息、任务和请求编号。它先把用户消息保存到数据库，并将任务置为 `running`，再启动执行。这样，即使浏览器断开，服务器也知道自己已经接收了哪条要求。

同一个任务正在运行时，不能再插入另一条新要求。`requestId` 重复且内容相同，则返回“已有请求”的记录，不再另发一次模型任务；相同编号配了不同内容会被拒绝。

消息送到执行器时，上层只需要表达：

```text
在这个 executionSessionId 中，执行这段 message，并把事件通知我。
```

`local-pi-runtime.mjs` 负责把这句话落实为 SDK 调用、项目目录和会话文件。任务服务不需要理解 Pi SDK 的内部方法。将来接入 Agent Compose，主要替换这个执行实现，上层任务流程可以继续沿用。

## 5. 为什么有四种不同的编号

这些编号不是重复命名，而是在区分不同对象：

| 编号 | 标识什么 | 什么时候沿用或改变 |
| --- | --- | --- |
| `task.id` | 网页里的一项工作，例如“计算这组数的统计结果” | 在同一任务中一直沿用 |
| `executionSessionId` | 负责该任务的执行会话，关联工作目录与运行元数据 | 当前与任务长期绑定；正式架构中由执行平台管理 |
| `piSessionId` | Pi 自己的一段模型对话 | 同任务续问打开原 Pi 会话时沿用 |
| `runId` | 某一条用户消息引发的一次运行 | 每次实际执行生成新的编号 |

例如同一个任务发送两条消息：网页任务编号不变，执行会话编号不变，Pi 对话编号应保持一致，但两次执行分别有自己的 `runId`。

`requestId` 另有用途：它识别用户的一次提交，服务用它避免网络重试造成重复执行。它不是上述任何一种运行对象。

目前的 `executionSessionId` 不表示已经有容器。执行器通过 `runtimeInfo()` 明确报告 `backend: "local-pi"`、`taskContainers: false`。

## 6. 多轮对话为什么需要两类保存

第一类是供网页读取的记录，位于 `runtime/tasks/tasks.sqlite`。SQLite 可以先理解为“保存在一个本地文件里的结构化数据库”，不需要另开一个数据库服务。本轮使用 Node.js 已提供的 `node:sqlite`，没有增加 npm 数据库依赖。

`task-store.mjs` 建立三张表：

| 表 | 保存什么 | 用在哪里 |
| --- | --- | --- |
| `design_tasks` | 任务标题、状态、各种执行编号 | 左侧列表与当前任务信息 |
| `chat_messages` | 用户要求、最终回答、顺序、请求编号 | 中间对话与消息去重 |
| `chat_run_events` | 说明、工具开始/结束、运行状态等 | 右侧执行动态与历史检查 |

第二类是供 Pi 继续执行的原生会话文件，位于 `runtime/pi-web/sessions/`。里面保存 Pi 理解的模型消息、工具调用和工具结果等上下文。

只把人类可读的最后回答存进数据库，并不自动等于恢复了 Pi 的内部对话。反过来，只保存 Pi 的事件文件，也不会自动出现网页任务列表。因此，两类记录分别承担职责。

当前 `pi-sdk.mjs` 的网页路径使用 `SessionManager.create()` 创建持久会话，后续通过 `SessionManager.open()` 打开同一个 `sessionFile`。每一轮可以创建新的 JavaScript 会话对象，执行后仍释放对象；下一轮通过磁盘文件续接对话，而不是要求某个内存对象永远存活。

CLI 的 `npm run pi:sdk` 练习仍使用内存会话，保留第 2 步的学习行为。网页与 CLI 使用同一段共享代码，但传入的保存方式不同。

## 7. SSE：为什么不用等最后一刻才显示

普通的一次性 JSON 响应要等任务结束，才把结果完整交回来。SSE 是“服务器在同一个 HTTP 响应中，陆续发送一条条事件”的方式。

这里仍然使用浏览器的 `fetch()` 发送 POST 消息，然后读取响应的数据流，并非另外建立一个新的聊天服务。

典型过程如下：

```text
task                  用户消息已经接收并记入任务
session               确认本轮执行会话、Pi 会话和 runId
run_status            开始运行
progress_message      执行过程中的可见说明
tool_start / tool_end 文件操作开始、结束
assistant_message     最终回答
run_status / done     本轮执行结束
message_saved         最终回答已保存
task_saved            返回保存后的任务状态
```

`done` 不等于整个响应已经结束。它表示执行器做完了，但应用还要保存回答和任务状态。如果网页读到 `done` 就关闭连接，可能错过后面的保存确认。

所以 `public/sse.mjs` 持续读到响应结束，并要求收到 `task_saved`。网络中途断开或尾部事件损坏时，页面不能声称已经完整收到结果。网页提供刷新和恢复入口；恢复发送沿用原请求编号。

本轮对齐原仓库默认执行路径的展示习惯：执行中的说明发为 `progress_message`，最终答案发为 `assistant_message`。SSE 表示事件持续到达，不承诺答案每个字都实时出现；页面解析器兼容 `text_delta`，当前 SDK 适配器主要发送完整的步骤说明与最终答案。

执行说明是模型公开输出的任务说明，不是隐藏思维链。工具卡片的开始和结束来自实际工具事件，不是根据回答文字猜测。

## 8. 刷新、断线与重启分别发生什么

刷新网页时，页面重新请求任务列表和任务历史。网页记住上次选择的任务编号，但对话内容和执行记录来自服务器数据库。若服务器仍在运行，页面显示“运行中”，输入暂时锁定；点击“刷新记录”可以读取之后发生的事件。

浏览器断线不会自动取消服务器上已经接收的任务。页面先保留待确认请求，恢复时核对原请求编号。这能避免“其实已经执行，只是没收到回答”时再次调用模型。

服务器正常停下后再启动，数据库和 Pi 会话文件仍在项目目录。若启动时发现某项任务还标记为 `running`，`recoverInterruptedTasks()` 会把上次运行记为中断失败，并写入相应记录。它不会假装模型正在继续，也不会自动重新执行那条要求。

“恢复已有对话”和“把中途断掉的运行从原步骤继续执行”是两种能力。本轮实现前者，并为后者记录失败状态；没有实现自动恢复中断任务的调度机制。

## 12. 距离原仓库正式架构还差什么

当前已把任务入口和执行器分开。正式目标是把执行边界后面换成：

```text
任务服务 → Agent Compose → 独立任务容器中的 Pi
```

Agent Compose 在这里负责外部执行会话与运行管理。容器为每项任务提供单独的执行环境，涉及镜像、启动命令、文件挂载或同步、状态检查、停止和资源释放。它不是只把 `local-pi` 改一个名字就完成的事情。

本轮只读环境检查记录：服务器存在 `/usr/bin/docker`，但 `hanwen` 访问 `/var/run/docker.sock` 被拒绝，当前没有可用 `agent-compose` 命令。正式接入前需要解决 Docker 使用权限，并确认运行时、镜像与任务文件的存储安排符合项目范围约束。本轮没有改变系统用户组、Docker 守护进程或项目外状态目录。

当前 read/write 仍由应用检查文件范围，并非操作系统级容器沙箱。工具注册、专业软件依赖、工具版本治理、停止按钮、人类反馈与自进化也尚未在这一轮实现。后续仍按原仓库实际文件逐项重建、解释和验证。
