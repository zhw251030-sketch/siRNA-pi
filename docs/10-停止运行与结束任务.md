# 第 6 步：停止本轮与结束任务

日期：2026-10-20。本步继续第 5 步 D 的网页 → Agent Compose → 容器 Pi 链路，补上运行中的控制。没有新增模型、软件依赖、系统权限或分支。

## 先理解这次解决什么问题

上一轮已经可以在网页发送消息、看到工具操作、继续追问。但是，发出去的任务如果方向不对，只能等待；完成后容器仍占用运行资源，也没有网页入口结束它。

这次加入两个按钮：

| 操作 | 停止本轮 | 结束任务 |
| --- | --- | --- |
| 日常理解 | 请先停下，我还想继续改要求 | 这件事到此结束，把运行环境收起来 |
| 当前执行 | 请求中断，并确认后台终止 | 有执行时先请求中断、等待记录保存 |
| 容器 | 保留，方便续聊 | 确认释放 |
| 对话、工具轨迹、文件 | 保留 | 保留 |
| 后续消息 | 停止确认并保存后可继续 | 当前任务只读；需要执行时新建任务 |

这不是让大模型理解“停止”两个字后自行决定是否听话。按钮通过程序控制真实执行进程；模型不负责决定是否释放自己的容器。

参考应用代码基线仍为 `965c53fba4eaa23996f54aa0532c7f6e1064bfd8`，参考仓库当前检出为 `67d275494c50f1e5c205b96b72a7b1623acfbe1d`。以下路径相对于参考仓库。

特别是：参考应用会调用 `sandbox rm`；当前官方版本的 `sandboxstore/sandbox_metadata.go` 中，删除 sandbox 会执行 `os.RemoveAll(sandboxDir)`，连工作区和 Pi 会话一起删除。因此学习版使用 `sandbox stop --graceful <sandboxId>`，配合已有 `stopped_runtime_policy: remove` 释放容器，保留宿主机目录。然后检查 `vm_status=stopped` 和 `stopped_runtime_state=released`。接口名 `remove()` 表示结束运行环境，不表示删除任务文件。

## 一次停止请求怎样经过代码

```text
网页点击“停止本轮”
    ↓ POST /v1/tasks/:id/cancel
HTTP 路由校验请求
    ↓ cancelTask(taskId)
任务层找到本轮控制器，发出取消信号
    ↓ runtime.cancel(executionSessionId)
运行时把取消意图交给当前 RPC
    ↓ StopRun(真实 runId)
Agent Compose 请求终止容器里的本轮进程
    ↓ 最终流事件 / GetRun 确认终态
保存运行事件 → 保存聊天记录 → task_saved
    ↓
网页恢复输入，可以继续提问
```

要区分三个编号：网页任务的 `taskId`、执行会话的 `executionSessionId`、每次执行的 `runId`。同一任务的执行会话和容器可以一直相同，而每轮都有新的 runId。停止的是这一轮，结束的才是任务环境。

## 逐个文件理解

### 1. 页面为什么不只加两个按钮

`public/index.html` 增加“停止本轮”“结束任务”和帮助文字，`public/style.css` 设置按钮排布与不可操作状态。

`public/app.js` 的 `changeLifecycle(action)` 负责发送两个请求。这里增加独立的 `lifecycleBusy`：发送消息时，原来的 `busy` 一直持续到 SSE 结束；如果停止按钮也受它禁用，就会出现“运行时恰好不能停止”的错误。

点击停止后，页面显示“停止请求已接收”，继续接收原来的 SSE。它不会主动断开连接来冒充停止。断开浏览器只会失去画面，DETACH 模式下的执行仍可能继续。

`public/lifecycle.mjs` 集中保存几个容易出错的页面规则：

- Compose 任务才启用新按钮，旧 SDK 任务不声称具备未实现的功能。
- “已结束”是永久状态；稍晚到达的旧消息不能把它改回“运行中”或“可继续”。
- 结束任务后，未送达的文字保留为本地草稿，并解除全局待发送锁，避免影响新任务。

如果一个工具只有开始事件，没有完成事件，页面在本轮结束后显示“结果未确认”；中断时显示“已中断，结果未确认”。它不会把中断的写文件操作直接标成成功。

### 2. HTTP 路由为什么保持很薄

`apps/api/router.mjs` 新增：

```text
POST   /v1/tasks/:id/cancel   → { task, stopRequested }
DELETE /v1/tasks/:id/runtime  → { task }
```

路由检查同源访问、空请求体和任务存在性，再把操作交给任务层。它不处理 Docker 或 Pi 内部细节。错误返回经过整理的提示，不把底层命令错误和私有路径原样发到网页。

路由还跟踪已接收的生命周期操作：即使浏览器中途断开，正常关闭网页服务时也要等它们完成，避免执行到一半丢掉保存。

### 3. 任务层为什么要“等一下”

`packages/task-core/task-message-service.mjs` 每轮创建一个 `AbortController`，可以理解为本轮的“停止开关”。它还保存本轮完成的 Promise，可以理解为“执行和记录保存全部结束的通知”。

`cancelTask()` 触发停止开关，但不会立刻把数据库改为空闲。`endTask()` 则先占住结束锁；如果还有本轮执行，先停止并等待完成通知，再释放容器。

这是为了避免两个竞争：

1. 用户点停止后立刻发送新消息，而旧进程还没退出。
2. 容器已经释放、任务已经结束，迟到的聊天保存又把任务改回可继续。

`packages/task-core/task-store.mjs` 也保留一道保护：对话仍可以落盘，但 `stopped` 不能被迟到的成功或失败更新覆盖。历史消息和执行编号不会因为结束任务而清空。

### 4. 运行时管理的是“任务与真实执行”的对应关系

`packages/agent-runtime/agent-compose-runtime.mjs` 增加 `cancel()`、`remove()` 及运行/取消/释放中的互斥记录。

- 正在初始化时点停止：允许已经提交的固定目录初始化命令收尾，随后不再提交模型任务。初始化本身不调用模型。
- 已获得真实 runId：针对它发送停止请求；不能拿网页临时生成的 UUID 去停止另一个系统里的运行。
- 网页服务重启：利用磁盘上的执行关系查找仍未确认的后台运行；一次未提交成功的重试不能覆盖真正需要停止的 runId。
- 无法确认停止：保留未确认状态，不伪造成功，也不自动重试付费任务。
- 结束任务：先确认容器释放、目录仍在，再保存 `status: stopped`、`runtimeReleased: true`、`endedAt`。

`runtime-router.mjs` 负责把这些操作转发到 Compose，并拒绝对旧 SDK 任务调用未实现的停止/释放。`runtime-port.mjs` 记录上层依赖的接口。

### 5. RPC 为什么收到响应还不能马上完成

`packages/agent-runtime/agent-compose-rpc.mjs` 的 `StopRun` 返回可能仍是 `running`。因此新增 `getRun()` 和 `stopRunAndWait()`：停止请求发送一次，随后通过最终事件或状态查询确认终态。单次状态请求有独立的最长 10 秒截止时间，停止确认默认最多 15 秒。

收到停止意图时如果还没有后台 runId，先记住这个意图，等 `started` 到来后再停止。正常完成与停止恰好同时发生时，保留真实的正常完成结果，不一概改成“已中断”。

本轮真实测试还发现官方版本的差异：Docker 中断产生 `context canceled`；prompt attach 把它转换成普通错误，使控制服务可能保存为 `failed`。学习版仅在本地有明确停止意图、后台已进入终态、错误精确为 `context canceled` 且没有清理错误时，将业务状态解释为 `canceled`，并保存原始后台状态。普通失败仍为失败。这是对确定语义的版本适配，不是把所有失败都改成中断。

### 6. 执行器如何确认容器真的释放

`packages/agent-runtime/compose-executor.mjs` 的 `release()` 使用官方 CLI：

```sh
sh scripts/project-agent-compose.sh sandbox stop --graceful <sandboxId>
sh scripts/project-agent-compose.sh inspect sandbox <sandboxId>
```

程序检查环境编号一致、运行状态为 stopped、资源状态为 released。只看到第一条命令返回，不足以证明容器已经释放。原始释放结果也会保存：温和停止超时后平台可能升级终止方式，不能一律声称所有进程都自然退出。

## 数据保留在哪里

以下都是服务器项目 `/home/hanwen/Project/project/siNRA-pi` 内的路径，不进入 Git：

| 位置 | 保存什么 |
| --- | --- |
| `runtime/tasks/tasks.sqlite` | 网页任务、聊天内容、运行事件 |
| `runtime/compose-sessions/<executionSessionId>.json` | 任务与容器、Pi 会话、各轮执行的对应关系及结束状态 |
| `runtime/compose-web/*.events.jsonl` | 每轮转成网页格式的执行事件 |
| `runtime/agent-compose/data/sandboxes/<日期>/<sandboxId>/workspace` | 输入、工作和输出文件 |
| 同 sandbox 的 `state/agents/providers/pi/sessions/*.jsonl` | Pi 的真实会话上下文 |

容器是运行进程的地方，上述文件放在挂载的宿主目录里。所以释放容器可以保留结果。它也意味着“停止”不等于撤销：停止前已经写入的文件不会自动恢复旧内容。

## 验证方法与实际记录

离线测试覆盖真实本机 gRPC 服务、临时 SQLite 和 HTTP 服务，以及页面状态规则；不能把它们替代成服务器实际中断验证。

真实验收顺序：先用新的专用任务完成统计文件及对话标记；中断一轮只读任务；确认同一 Pi 会话仍能回答此前标记；再在运行中结束任务；最后检查容器消失、对话和文件还在、刷新后只读。

`scripts/verify-compose-lifecycle.mjs` 是只读验收程序。它对照首次统计的基线，检查：任务/容器/Pi 编号、后台终态、活动运行数量、JSONL 旧内容前缀、统计文件、保存的事件、容器存在或释放状态。它不会调用模型，也不会主动停止任务。

```sh
node scripts/verify-compose-web-task.mjs <taskId> > runtime/compose-web/lifecycle-baseline.json
node scripts/verify-compose-lifecycle.mjs <taskId> canceled runtime/compose-web/lifecycle-baseline.json
node scripts/verify-compose-lifecycle.mjs <taskId> resumed runtime/compose-web/lifecycle-baseline.json
node scripts/verify-compose-lifecycle.mjs <taskId> ended runtime/compose-web/lifecycle-baseline.json
```

该脚本针对上面的特定四轮验收序列，不是任意历史任务的通用成功判断器。本轮实际基线文件名为 `lifecycle-v2-baseline.json`。

## 当前边界与下一步

如果首次对话在 Pi 保存会话前就被过早中断，可能没有可恢复的完整上下文。程序会保留记录并拒绝悄悄新建空白上下文；这不应被说成“所有位置停止都能无损恢复”。停止也不会撤销已发生的模型费用或文件写入。

这仍是通过 SSH 隧道使用的个人学习服务。没有新增多用户认证、公开域名、容器配额、开机自启、文件下载界面或自进化能力。旧测试任务的运行环境不会因新增按钮被批量释放。

下一步建议先对照原仓库完成任务文件的查看与结果获取：把已经保存在容器工作目录里的输入/输出展示到网页，继续理解任务文件如何进入和离开执行环境。随后再进入“把软件封装成工具”的第二项贡献。文件接口应继续沿用原仓库的职责与路径检查方式，下一轮核对具体实现后逐步完成。
