# 第11E步：自动观察与候选冷却

本步把“有人去点独立审查”推进到“开启开关后，系统观察新结束的任务轮次并自动送审”。原来的 Pi、工具报告、证据预览和 Curator 都继续使用；新增的是负责连接它们的协调器。Builder 交接、工具验证与批准仍由人明确触发。

## 先用一个例子理解

假设某个任务反复调用同一类业务工具，或者 Pi 明确调用 `report_tool_gap` 报告缺口。此前这些记录要等你打开预览，再点击“提交独立审查”。现在你可以先开启全局自动审查；任务结束并保存以后，协调器检查这一轮是否符合既有规则，符合才交给 Curator。

Curator 仍是一次独立模型审查：它读取冻结证据和已有工具目录，返回 `candidate` 建议或 `skip`。协调器并不自己推理应该开发哪个工具，也不会把普通聊天文本直接当成工具需求。

若第一个任务已有“序列质量摘要”候选，第二个任务的 Curator 又建议同一能力，后端检查过去七天的候选，保留原候选，把第二次的最终结果记为 `skip`，写明“后端冷却规则”和原候选编号。这是防止短期内反复产生同类建议的规则，不能保证两种语义相近但名称不同的能力也会合并。

注意顺序：第二次模型已经回答了，才发生候选冷却。因此，冷却不会省掉这一次模型调用。本步另外设置自动送审次数，控制自动触发的数量；次数也不是人民币或 token 的精确预算。

## 原仓库怎样做

本步对照固定版本 `sirna-pi-agent-service-refactor@67d275494c50f1e5c205b96b72a7b1623acfbe1d`，没有改动参考仓库。

| 参考文件 | 实际行为 | 本步对应 |
| --- | --- | --- |
| `packages/task-core/task-message-service.ts` | 清除执行占用后发出 `onSettled`，通知异常不影响原任务 | 消息服务增加同职责回调 |
| `apps/api/router.ts` | 连接任务完成与协调器；排除自动构建消息；确认运行环境空闲；管理启动和关闭 | bootstrap/lifecycle 接线及同步占用复核 |
| `packages/extensions/tool-curation/tool-curation-coordinator.ts` | 接收结束轮次、安排审查、检查同能力七天冷却 | 独立 coordinator 与现有串行 service 协作 |

原版还连接自动 Builder、Goal 执行期间的限制和验证后的回调；这些不在本步。学习版采用默认关闭、每次服务启动最多三次自动尝试、重启不回扫历史等更保守的启用方式。原版近期判断使用完成时间或请求时间；本步只使用完整候选的合法完成时间，并排除未来时间。

## 一轮任务怎样走过这些文件

### 1. TaskMessageService：先把原任务收好

文件：`packages/task-core/task-message-service.mjs`。

底层 `done` 只表示执行器报告结束，后面可能还有文件收集和消息入库。因此不能在刚收到 `done` 时立刻启动自动审查。

新的顺序是：执行结束 → 尝试收集文件 → 保存助手消息 → 清除 active 占用 → 调用 `onSettled`。文件归档未确认时保留已有警告语义，不冒称文件同步成功。只有确实保存了助手消息才通知；重复发送同一请求、消息保存失败都不会重复通知。回调拿到当次的 task/run/userMessage/requestId，而不是事后读一个可能已被新轮次替换的编号。

回调异常或返回被拒绝的 Promise 不改变原任务结果：已经保存的回答不会因为后台观察出错而变成失败。`isTaskBusy(taskId)` 则把执行、上传、取消、结束预约和持久状态汇总为同步只读检查。

### 2. coordinator：决定这一轮能否自动送审

文件：`packages/extensions/tool-curation/tool-curation-coordinator.mjs`。

`observeRun` 接收通知，`runOnce` 串行消费队列。检查包括开关、固定来源、是否为 Builder 消息、任务是否仍是这次轮次、真实运行环境是否空闲、证据是否完整合格，以及是否已有同轮审查。观察本身不等于模型请求。

自动审查复用原来的资格规则：同类完整业务调用至少三次且输入至少两种，或者错误至少两次；有效缺口报告也能单独触发。普通文件读写和管理操作不因重复就成为业务工具线索。自动触发中，有报告或合格信号包含错误时用 `online_gap`；其他重复信号用 `post_run`。

确定要送审时先同步扣一次尝试，再调用原 service。失败或结果未知不退次数，不自动重试；最多三次之后关闭。已存在同轮记录会直接去重；与人工同时竞争时，最后可能只是取得已有记录，但已预留的尝试仍保守计数，不能把这个数字当成真实模型账单。

队列最多32项，一次进程最多记住256个 task/run 键，最近状态只保留20条。容量耗尽会关闭自动准入；不会通过丢弃旧去重记录让同一轮再来一遍。临时观察状态不写另一份数据库；重启后开关关闭，不回扫历史。已有 Curator 记录仍由原数据库持久保存。

### 3. readiness：为什么检查两次还不够

文件：`apps/api/service-lifecycle.mjs`、`apps/api/bootstrap.mjs`，以及 coordinator 的最终准入位置。

运行环境检查要等待 Agent Compose 返回。等待前后都要确认 task 没被执行、上传、取消或结束占用。审查发现，仅在 async readiness 内最后检查一次仍有窗口：它返回 Promise 后，另一段排队的代码可以先取得上传预约，然后 coordinator 才继续。

修复是在 coordinator 恢复执行后，再通过同一个 TaskMessageService 做同步 `isTaskBusy` 检查；从这个检查到冻结预览、预留次数、调用 request 之间没有 `await`。测试用真实上传/取消/结束预约重现了旧行为，保证忙时不花次数、不送审。

bootstrap 明确设置一秒检查间隔、三次自动尝试和七天冷却。HTTP 真正监听成功以后才启动服务；关闭时先同步停止观察准入，再排空已有任务与 Curator，最后关闭数据库。关闭开关不会取消已经接受的审查，也不会恢复次数。

### 4. service、store、evidence：沿用证据链，增加冷却

文件：`tool-curation-service.mjs`、`tool-curation-store.mjs`、`tool-curation-evidence.mjs`，都在 `packages/extensions/tool-curation/`。

service 继续负责不可变请求、task/run 唯一性、串行模型执行、身份和清理确认。新增内部 `find` 精确查同轮记录，不受网页最近100条展示窗口影响；`request` 的内部 automatic 标记只影响合法触发类型，公开请求格式未扩大。

store 的 `findRecentCandidate` 在持久候选中检查精确 capabilityKey、其他候选编号和包含两端的七天完成时间范围，不只查最近100条。采用记录前重新核对冻结 trace、结果绑定和时间；损坏记录导致拒绝继续，不能被当作“没有重复”。没有修改旧 SQLite schema 或旧记录。

模型返回后先校验身份、结果与清理，再查询冷却并保存最终结果；串行 worker 中这一段没有异步让出点。命中后构造新的标准 skip 结果，明确归因给后端，保留原始模型回答对象；实际运行的原始回答仍在既有私有事件/原生会话。skip 不作为冷却锚点，所以连续重复不会无限延长原候选的七天期限。

evidence 只增加合法触发类型覆盖，并对最终 trace 重新计算摘要、检查64KiB上限。未指定覆盖的旧路径保持原有格式，不改写历史冻结证据。

### 5. HTTP 与网页：让用户能控制自动行为

文件：`apps/api/router.mjs`、`public/curation-automation.mjs`、`public/app.js`、`public/index.html`。

`GET /v1/tool-curation-automation` 只读状态，`POST` 只接受 `{ "enabled": true }` 或 false；不接受调整额度、提示词、工具权限或其他字段。正文限制1024字节，沿用本机 Host/Origin 边界。异常只返回安全提示。

新面板展示开关、已用/剩余次数、队列和最近送审编号。页面初次只 GET；没有后台轮询、自动 POST 或失败重发。过期 GET 不能覆盖更新后的开关状态；POST 结果未知时先 GET 核对，确认失败则保持控制禁用，等待手动刷新。

“已送审”只代表请求被接受；最终 candidate、skip 或 error 仍去任务的“刷新审查记录”查看。手动审查仍走原入口，不计自动次数；七天冷却则同时适用于新完成的手动和自动审查。

## 现在怎样使用

打开本机 SSH 隧道入口 `http://127.0.0.1:3000/`，点击顶部“自动审查”。默认应显示关闭、0/3、剩余3次。需要时显式开启，再在新任务或原任务中发送新一轮消息。只有启用期间新结束、且证据合格的轮次会自动送审。

完成后可点击“刷新自动审查状态”，再选择对应任务点击“刷新审查记录”。关闭再开启不补次数；刷新浏览器也不补次数；重启 API 后重新从关闭状态开始，不自动处理以前遗漏的轮次。Builder、验证、批准的既有人工入口继续使用。
