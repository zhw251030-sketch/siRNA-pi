# 第10I步：工具版本发布与人工回退

本步接续第10H步已经通过验证的候选：已把新增碱基计数的工具发布为1.0.1，保留1.0.0，并完成真实人工回退及恢复。当前active为1.0.1，1.0.0为inactive/retained。个人Git仍只有main；工具版本与Git分支是两回事。

## 先区分两种版本

Git main提交管理应用代码；工具的1.0.0/1.0.1管理应用中某个可调用程序的正式产物。二者不是同一编号。切换工具不需要把整个Git仓库回退，更不需要删除新版本代码。

上一轮已有verified候选，但它还没有正式版本号。verified说明记录中的检查通过；approved说明被批准为正式版本；active说明当前通过目录对外提供。旧版本即使inactive，仍然可以是已批准且材料完整的历史版本。

## 对照原仓库

只读参考基线67d2754。tool-registry.ts:767的nextVersion给首版分配新toolId/1.0.0，后续复用父toolId和major/minor，以所有历史版本最大patch加1。所以回退到1.0.0之后再发布，不能重新占用已有1.0.1。

tool-registry.ts:782的activateVersion把旧active转inactive，插入新active、更新提案approved和写事件；tool-lifecycle.ts:1230负责证据检查、正式包和catalog。原仓库批准即激活。重复批准历史提案只返回原登记，不重新激活。

tool-registry.ts:843及tool-lifecycle.ts:1533提供人工rollback：选已有保留版本，改active并写事件，不生成版本或重新验证。原实现还支持disabled目标、拒绝degraded和已释放产物，另有运行时退休和自动降级策略。本步只实现active/inactive及retained，未引入这些后续治理功能。

我们沿用职责分层和主流程，并保留学习版更严格的材料核对：回退前读回真实目标证据；旧目录缺失/不一致时拒绝发现，不能绕过目录扫描历史包。对已active版本再次回退为检查后的幂等操作，不增加重复切换事件。这些是本学习版的边界，不称原仓库具有完全相同实现。

## 文件一：tool-registry.mjs，把“只存首版”改成“保存历史”

原schema3的tool_versions要求version只能1.0.0、state只能active、toolId和toolName各自唯一。只修改JavaScript中的版本字符串无法放入第二版：数据库本身会拒绝。

schema4让同一toolId可以拥有多个version，同名版本唯一，提案只能对应一个正式版本，同时每个工具最多一个active。child版本记录parentToolId/parentVersion。父关系还存在原提案和验证报告；本步的版本行及新manifest.parent为学习版新增的追溯位置，原仓库主要把父关系存在proposal登记中。

升级先用SQLite一致性快照备份（包括已提交的WAL内容），再用事务替换旧约束并复制原记录。备份留在项目runtime/tool-registry，不进入Git。事务意味着步骤中某一项失败时，数据库内这一组修改一起撤回；它不意味着文件系统、数据库和catalog三个系统合成了一个全局事务。

发布时同一数据库事务完成：核对提案/最新验证及父身份 → 原active转inactive → 插入新active → 提案改approved → 写version_activated。回退事务只切换状态并记录actor、reason和目标，不修改原批准身份。

## 文件二：tool-approved-packages.mjs，给新版本独立的正式包

每版仍由五个文件组成：manifest.json说明身份，tool.mjs保存源码，verification.json保留验证报告，approval.json保存批准记录，integrity.json保存摘要。

目录从固定toolId-1.0.0推广为toolId-version。发布1.0.1新增独立目录，原1.0.0五个文件不重写。新包的源码与已经验证的候选源码相同，验证报告也按原字节带入，避免“验的是A，发布的是B”。

## 文件三：tool-lifecycle.mjs和tool-validation-reports.mjs，历史可读与当前可用分开

上一轮只支持active1.0.0作父版本。若直接切换为1.0.1，1.0.0转inactive后，孩子报告再去读父证据就会失败。因此历史读回现在允许保留的active/inactive版本。

这不代表inactive也会被Agent调用。历史读回检查“文件和身份是否完整”；catalog和执行入口检查“是否当前active”。递归核对父链时还有顺序/循环保护，避免坏数据使读报告陷入无限递归。父版本的源码、镜像和包摘要继续与原验证绑定一致。

读回最多允许64个正式版本组成的父链。这个保护同时约束发布：计算新孩子的深度时必须把孩子自己算进去，否则会出现“登记成功，但永远读不回来”的坏版本。共享的tool-version.mjs统一检查版本号、父子顺序及维护操作文本；这里只接受规范的三段非负整数版本号，不接受前导零、预发布后缀或超过安全整数的值。

## 文件四：tool-approval-service.mjs，组织发布与回退

批准服务读材料和通过报告，分配新版本，发布不可变包，再执行数据库事务，最后刷新目录。重复批准已inactive的旧提案会返回它真实的inactive状态，不把它重新激活。

rollbackRegisteredTool先完整核对目标，再调用数据库切换并刷新catalog。actor和reason记录“谁因为什么做了切换”，不代表新增了网页登录或多用户身份认证。可信CLI仍由服务器hanwen执行。

如果数据库已完成切换，而目录写入随后失败，服务必须明确报告状态已生效。恢复方式是检查实际状态并显式重建catalog；不能伪称整个批准已经撤销，也不能盲目再创建一个版本。未登记的残留包不会自动进入工具列表。

## 文件五：CLI、调用与审计

scripts/manage-tool-proposals.mjs增加rollback命令。服务器唯一目录内的示例：

```sh
npm run tools:proposals -- approve 4530af22-d8d7-42f0-ac75-fec6ce851466 hanwen-via-codex
npm run tools:proposals -- rollback summarize_target_sequence 1.0.0 hanwen-via-codex "restore retained parent"
npm run tools:proposals -- rollback summarize_target_sequence 1.0.1 hanwen-via-codex "restore approved new version"
```

这些是写操作，展示用法，不是需要重复运行的验收命令。回退到较新的已有版本也使用同一选择机制，不产生1.0.2。

tool-run-audit.mjs接受正式多版本号，记录每次真正执行的是哪个版本和镜像。tool-approved-execution.mjs在执行前后核对active绑定，并在目录检查后的版本读取处显式检查state。这个检查不能再依赖历史读取函数，因为历史读取本来就允许inactive。若执行过程中另一个管理进程切换了active，本次调用会按原有规则判失败并留审计；目前没有跨所有进程的统一维护锁，所以实际切换应在空闲时进行，不能声称已消除所有进程间切换窗口。

## 真实验收的设计

三个阶段在同一个宿主stdio MCP客户端进程中进行，输入固定为AACCGGGUUUA：

| 阶段 | active | 独立预期输出 |
|---|---|---|
| 批准新版本 | 1.0.1 | length11、GC5/11、A3/C2/G3/T3 |
| 回退旧版本 | 1.0.0 | length11、GC5/11，无counts字段 |
| 恢复新版本 | 1.0.1 | 与第一次相同 |

T包含原来的U，因为沿用U→T归一化。测试检查新列表描述、真实输出、审计版本/镜像/摘要、容器限制和执行后移除。用同一MCP进程说明调用无需重启MCP客户端才认识切换。

本轮不重新构建候选、不重新验证旧案例、不调用模型。网页后端需在空闲时重启一次加载兼容schema4的新代码；该部署重启与之后通过catalog切换工具是两回事。旧guest及任务元数据保留。本轮真实业务验收走宿主正式MCP路径，不冒称已经进行了新的网页Pi模型对话。

## 本轮发现的问题与保留的诊断

初次Windows全套1021项通过1008、跳过13，随后Linux全套通过1018、失败1、跳过2。失败的CLI守卫测试继承了当前目录：在Windows会被拒绝，但在正确Linux主机、用户与项目目录里实际进入了维护命令。它对当前1.0.0发出同版本回退，没有切换工具或执行业务，却提前触发schema3→4迁移和catalog重新生成。这是测试隔离错误，不能把第一次Linux结果写成全部通过。

事故后的只读检查确认：四张登记表的原字段和值全部未变，父列新增为null；原active仍为1.0.0，新增事件和业务执行均为0；一致性备份保持原schema3且全部原行相同。13份旧材料、6份旧审计文件、11份会话元数据、4个运行容器、任务表哈希及凭据元数据未变。证据保存在runtime/version-release-early-migration-check.json；原失败日志保留。修正后的测试显式使用独立临时目录，再也不会继承正式项目目录。

独立审查另复现两个边界问题：目录检查与版本读取之间切换active可能启动旧工具；第65层候选可能先登记成功再因读回深度超限失败。前者在执行边界单独检查active，后者必须在写入前及事务内计算包含新孩子的链深度。负例验证应检查“没有启动执行”和“没有产生包/登记/事件”，而不只是最后返回了错误。

## 下一步的边界

完成本步意味着已有“验证候选→批准新版本→使用→人工回退”的工具版本流程。仍没有让Agent自己分析失败、产生修改、提交候选并在授权规则下循环改进；自动降级与运行产物退休也尚未实现。下一步应继续对照原仓库的工具构建/提案协调器，学习怎样由Agent发起这一流程，并保留人的批准边界。
