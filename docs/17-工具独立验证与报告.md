# 第10D步：从已提交提案到有证据的验证结论

## 这一步为什么存在

第10B步构建镜像并运行样例；第10C步把候选、基线、测试和镜像信息固定为材料快照，登记为submitted。第10D步从这个编号重新读取固定材料，通过独立验证流程决定verified或verification_failed。

构建证明“制作出了一个能运行样例的成品”；登记证明“收到了哪份材料”；独立验证回答“在声明的条件、案例和比较对象下是否满足全部门槛”。这三个动作不能互相代替。verified仍不等于approved，也不会让新工具自动出现在Pi的MCP工具列表中。

## 与原仓库的对应

参考application965c53f/checkout67d2754，不复制应用代码。保留tool-lifecycle.ts的sirna-tool-validation/v3主要报告字段和关卡顺序，tool-registry.ts的验证记录/状态/事件事务，以及已有tool-validation.mjs的输出匹配和重复性判据。本轮把原大型生命周期文件中的检查、执行和报告保存拆成较小文件，保留职责关系。

当前明确只支持已有教学范围：候选和基线均Node、无额外依赖、no_external_access、exact、有真实runtimeArtifact，每组1至10个案例、单次业务输入不超过64KiB。Python/Bash、依赖安装、联网/外部软件权限暂不执行；请求超出范围明确拒绝，不默默跳过关卡后宣称通过。

## 文件一：tool-validation-static.mjs，先看代码要求什么能力

assertValidationSupported确认执行器支持该合同。checkValidationSource分别扫描候选和基线，寻找HTTP/原始网络、外部进程、动态执行、Docker控制接口、运行时安装、敏感绝对路径等模式；报告保留规则ID、目标文件和行列。

这是词法扫描，像在文本中找特征，不是完整理解程序。注释中的词也可能触发，混淆写法也可能绕过；静态检查不能单独证明安全。容器的权限与资源限制是另一层实际约束。

## 文件二：tool-validation-runner.mjs，真正执行的容器边界

createDockerValidationRunner提供两个接口：checkSources检查两份源码语法及运行产物；run执行一次候选或基线并返回结果。服务层安排何时调用，执行器负责怎样运行。

候选使用上一轮真实镜像，但必须核对镜像固定摘要、构建编号、创建时间、基础镜像、命令和源码标签，还要读取镜像内/opt/tool/main.mjs计算实际摘要，与manifest.scriptSha256相同。否则“静态检查A代码、实际运行B镜像”会让验证失去意义。

基线从已登记baseline.mjs读取，放入固定Node底座的独立容器；不借用候选镜像执行，也不在服务器宿主直接运行。双方使用相同基础Node环境与运行限制。

每次运行使用新容器和新工作目录。实际inspect检查无网络、无宿主挂载/凭据/socket、非root执行、只读根文件系统、1GiB内存/64进程和64MiB临时空间。固定可信助手用root准备只读基线/助手和读取摘要；候选/基线本身始终以65534运行。CPU配额仍不可用，不能宣传为完整敌对代码沙箱；当前入口只用于审阅过的教学源码。

scripts/lib/tool-validation-guest.mjs是容器内固定助手，负责有界子进程结果、工作目录摘要等。stdout/stderr合计最多64KiB；输入封装包含变化的toolCallId和固定业务input。输出必须是单个JSON对象，非零退出、超时、输出超限或无法核对文件均不能通过。

只删除当前调用得到且标签归属一致的临时容器，删除后再确认不存在。旧网页容器、成品镜像与提案材料保留；清理不确认就报错。

## 文件三：tool-validation-service.mjs，安排七项关卡

validateRegisteredToolProposal只接收已登记提案编号，读取数据库和材料，不接受另外传入一份未登记代码替换它。

| 关卡 | 本轮含义 |
| --- | --- |
| 材料完整性 | 执行前后都核对材料与登记摘要，执行期间改动不能通过 |
| 静态检查 | 候选和基线都满足本权限档位的词法规则 |
| 语法 | 两份源码均通过容器内node --check，不因此执行业务代码 |
| 依赖 | 当前只接受空依赖；报告dependencyChecks为空，范围明确说明无声明依赖 |
| 重复性 | 同一smokeInput跑两次，两次成功且stdout/stderr/filesDigest相同 |
| 领域案例 | testCases每一项候选输出都满足expectedOutput |
| 基准净增益 | 同一benchmarkCases分别运行候选和基线，计算通过案例数之差 |

输出匹配沿用第10A步：对象预期是递归字面子集，数组长度和顺序需相同，数值不做隐式容差。不能把expectedOutput理解为JSON Schema。

教学例子有2个领域案例和2个基准案例，因此完整流程是2次烟测+2次领域+2次候选基准+2次基线基准，共8次业务执行。语法检查容器另计。净增益是candidateScore-baselineScore，要求至少1；这不是通用性能提升百分比，也不说明生物学活性。

这里“独立验证”指从固定材料重新执行检查，不采信构建阶段的成功声明；案例仍来自当前提案，并非独立隐藏测试集。因此它证明的是声明案例下的行为，不能直接推出未见输入上的正确率或科学有效性。

前置关卡未通过时不运行业务代码。运行错误分两类：工具自身非零退出、输出不合预期等形成失败报告；Docker传输、镜像身份、清理等基础设施错误会中止，保存诊断，不伪造完整验证结论。文件改变后的失败报告仍绑定原登记摘要，并明确artifactIntegrityPassed=false。

## filesDigest的含义与原项目差异

我们实际计算本次/tmp/work内目录名、文件名和文件字节的摘要，摘要前确认相关运行进程已结束；编码带明确内容边界，避免一个文件的内容伪装成下一个文件头。空工作目录才会自然产生空内容的SHA-256，不手工填写一个“通过用”的摘要。目录外临时文件不在这个摘要范围内。

原项目非镜像脚本路径也会摘要工作目录；原镜像控制器路径当前返回固定标记runtime-controller-no-persistent-files，因为没有持久文件传输。本学习版在镜像验证路径额外核对实际工作目录，这是明确的收紧，不声称两者逐字节实现相同。

## 文件四：tool-validation-reports.mjs，保存可以重新核对的报告

报告位于runtime/tool-artifacts/validations/<proposalId>/<validationId>.json。每次验证新编号，独占创建、私有权限、完成后只读，并计算整个JSON文件的SHA-256。失败诊断用独立.failure.json，未登记报告不会假装成为最新正式结论。

读报告时核对固定目录、普通单链接文件、大小、读取前后状态、摘要、提案/验证编号、结论及数据库最新状态。数据库提供的路径不能随意指向其他文件。报告上限16MiB。材料文件和报告文件分别有摘要：前者绑定被测对象，后者绑定测得的证据。

## 修改tool-registry.mjs，记住验证与状态

v2数据库增加tool_validations及tool_proposals.latest_validation_id。旧v1只读查询不迁移；验证写入路径显式migrate:true，先用SQLite一致备份保存包括WAL已提交数据的旧库，再事务升级，备份保留且权限0600。未知数据库版本或表布局拒绝。

recordValidation同事务完成：插入报告索引、把提案设为verified/verification_failed、保存最新验证编号、追加validation_passed/validation_failed事件。任一写入失败全部回滚。允许重新验证已验证或失败提案，历史报告保留；approved/rejected禁止验证。本轮尚无批准入口。

tool-lifecycle.mjs的show随之支持新状态，并实际读取报告后返回verified等标志。材料manifest仍是draft，因为验证改变登记状态，不篡改提交快照。

## 操作入口

在服务器使用已有Node24环境：

```sh
cd /home/hanwen/Project/project/siNRA-pi
npm run validate:tool -- f742eea2-b025-4474-ae47-d6eab267c408
npm run tools:proposals -- show f742eea2-b025-4474-ae47-d6eab267c408
```

## 下一步的边界

当前链路是“制作运行产物→登记固定材料→独立验证并保存结论”。下一步对照原仓库学习“明确批准→形成正式工具版本→允许Agent发现与调用”。验证回答是否达到约定门槛；批准回答是否决定把它纳入可用工具。当前approved/activated仍为false，网页和MCP工具列表没有自动增加新工具。自动提出修改、迭代验证和替换版本的自进化循环尚未完成。
