# 第13C-E步：受限 Evidence Store 与确定性 artifact 检查

## 这一阶段解决什么问题

13C-D 已经让网页可以发起验证请求，但 verifier 还缺少两种可复核证据：

1. 受控来源返回了什么内容；
2. 冻结文件经过什么确定性检查，检查时文件的哈希是什么。

如果只把 verifier 的文字写进 evaluation，之后无法区分“外部来源真的返回过这段内容”和“模型自己写了一条 URL”；也无法知道 JSON/CSV 检查是在什么文件版本上完成的。本轮先实现原仓库 EvidenceStore 的离线核心，保存回执和文件检查结果，但不执行网络访问。

## 与原仓库的对应关系

| 原仓库 | 学习版 | 作用 |
| --- | --- | --- |
| `packages/extensions/goal/goal-verification-store.ts:recordRetrieval/getRetrieval` | `packages/extensions/goal/goal-verification-store.mjs:recordRetrieval/getRetrieval/listRetrievals` | 保存检索类型、来源、响应正文和内容哈希，并按 verificationId 隔离 |
| `packages/extensions/goal/goal-verification-store.ts:recordCheck/getCheck` | `goal-verification-store.mjs:recordCheck/getCheck/listChecks` | 保存对冻结 artifact 的确定性检查和结果哈希 |
| `packages/extensions/goal/goal-verification-access.ts:checkArtifact` | `packages/extensions/goal/goal-verification-evidence.mjs:checkArtifact` | 读取不可变快照，执行有限检查，写入 check receipt |
| `goal-verification-access.ts:controlledFetch` | `goal-verification-evidence.mjs:safeUrl` | 当前只复用 HTTPS 学术域名 allowlist；真实 fetch、重定向和响应读取留到后续 |
| `goal-verification-evidence-resolver.ts:materializeRetrieval/materializeCheck` | 当前返回 `check:<id>` 证据指针，policy 接线留后续 | 先固定 receipt 形状，再接 verifier 的动态证据目录 |

原仓库的完整 Access Service 还包含 bundle、message、artifact、attempt、search、fetch 等接口，并要求 running 状态的短期 access token。本轮故意只开放 runtime 内部的 `evidence` 对象，暂不加 HTTP 入口或网络 fetch；网页只能看到验证 run 摘要，不能直接读取原始 response。

## 逐文件解释

### `goal-verification-store.mjs`：把证据变成数据库回执

新增两张表：

```text
verification_retrievals
  id, verification_id, kind, provider, query,
  source_url, fetched_at, content_type,
  content_sha256, response_text

verification_checks
  id, verification_id, artifact_id, operation,
  executed_at, artifact_sha256, result_json, result_sha256
```

`recordRetrieval()` 只接受正在运行且已经冻结 Bundle 的验证请求，保存前重新计算响应正文 SHA-256；同一验证、同一来源、同一内容哈希不会重复保存。`getRetrieval(id, verificationId)` 必须同时匹配两个身份，避免一个验证器读取另一个任务的来源。

`recordCheck()` 同样要求 running 状态，保存 artifact 当时的 SHA-256 和确定性结果的 SHA-256。这样数据库中的“通过”不能脱离具体文件版本解释。

### `goal-verification-evidence.mjs`：受限访问和 artifact 检查

这个模块只接受已经由可信调用方得到的 `responseText`，不自行调用 `fetch`。它先检查：

- URL 必须是 HTTPS；
- 主机必须属于原仓库的学术来源 allowlist（OpenAlex、Crossref、Europe PMC、PubMed、DOI）；
- 响应正文不超过 1.5 MB；
- verification 必须处于 `running`，且已经有 Bundle。

`checkArtifact()` 通过 `GoalVerificationBundleBuilder.readArtifact()` 读取快照，因此工作区原文件之后发生变化不会改变检查输入。支持的操作是：

- `exists`；
- `text_stats`，检查字符数和行数下限；
- `json_valid`；
- `json_array_length`；
- `csv_row_count`。

每次检查返回原始 check 记录，以及一个 `check:<uuid>` 证据指针。这个指针当前只作为后端 receipt 返回；下一步接入 Evidence Resolver 后，才允许 verifier 在 proposal 中引用它。

### `goal-verification-runtime.mjs`：把 Evidence access 放入可选扩展

启用 `SIRNA_GOAL_VERIFICATION=deterministic` 时，runtime 除了返回 Store、BundleBuilder、Coordinator 和 Goal port，还返回 `evidence`。默认关闭时这一层连数据库目录都不会创建。当前 deterministic fake verifier 仍只使用 Bundle 内的 artifact/tool/message 单元，因此新 receipt 不会伪装成已经完成的独立验证。

## 输入如何流动

```text
已冻结 Bundle + running verification
        ├─ evidence.recordRetrieval(预先取得的响应)
        │      └─ HTTPS allowlist → 计算 SHA-256 → SQLite retrieval receipt
        └─ evidence.checkArtifact(artifactId, operation)
               └─ 读取快照 → 确定性检查 → SQLite check receipt
```

模型在这一步没有权限把任意 URL、引文或检查结果直接写进数据库。它只能在后续通过受控 access 接口取得后端生成的 evidenceId。

## 验收

定向命令：

```text
node --test tests/goal-verification-evidence.test.mjs \
  tests/goal-verification-store.test.mjs tests/goal-verification-coordinator.test.mjs \
  tests/goal-verification-bundle.test.mjs
```

本轮 15 项全部通过，覆盖：

- retrieval 记录的 hash、verificationId 隔离和重开数据库读回；
- 非 allowlist URL 和超过 1.5 MB 的响应拒绝；
- JSON 数组长度检查写入 result/hash/evidence 指针；
- 快照被篡改时再次检查失败；
- pending 验证请求不能读取证据。

随后完整 `npm test` 结果为 1560 项测试、1544 项通过、16 项平台跳过、0 项失败。当前结果只证明本地回执和确定性检查可用，不证明网络检索成功、不证明外部来源内容真实，也不证明真实 Agent Compose verifier 已经能使用这些证据。

## 删除这一层会失去什么

删除 retrieval 表会使“模型声称看过来源”和“后端确实保存过来源响应”无法区分；删除 check 表会使 JSON/CSV 检查没有版本绑定；删除 `readArtifact()` 的哈希复核则可能把工作区后来篡改的文件当成验证时文件。它们是从“有一段模型解释”走向“有可重放证据回执”的基础层。

## 下一步

下一步对照原仓库实现短期 access token 和裁剪后的 bundle/message/artifact/check 读取接口，然后再把 controlled search/fetch 的网络边界接入。只有这层通过离线安全测试，才接真实 Agent Compose verifier；deterministic fake verifier 会保留为无网络回归夹具。
