# 第10E步：验证通过之后，怎样成为正式工具版本

## 先把三种状态分开

上一轮verified表示“这份提案在约定条件和案例下通过检查”。本轮增加approved，表示维护者明确决定采用这份提案；同时新增正式版本的active状态，表示工具目录当前选中该版本。active只是登记选择，Pi是否能够调用还需要后续MCP/执行接线，当前agentCallable=false。

这是确定性程序处理：读材料、核验摘要、写文件和数据库，不需要大模型判断批准，也不重新运行候选。用户已授权继续该学习步骤，本次批准人记为hanwen (delegated learning step)，明确是委托助手执行的学习操作。批准人文本是审计信息，不是登录认证或数字签名。

## 原仓库如何处理

参考application965c53f/checkout67d2754：tool-lifecycle.ts的approveRegisteredToolProposal先确认最新通过验证、报告和提案未变，再由tool-proposals.ts生成正式包；tool-registry.ts的activateVersion在事务中保存版本、更新提案并记录事件；writeActiveToolCatalog生成可用版本清单。后面的discoverApprovedToolPackages还要创建可执行AgentTool，不能把目录生成等同于Agent已接入。

本学习版保持这些职责、协议名称和主要字段，独立编写较小模块。本轮仅实现首个1.0.0版本；同名工具已有版本时拒绝再次首发，parent更新、旧版切换、禁用和回滚尚未实现。没有复制原应用源码。

## 文件一：tool-approved-packages.mjs，制作正式版本包

入口publishApprovedToolPackage接收已经核对的提案材料、验证报告原始字节、报告摘要、新toolId、批准人和批准时间。loadApprovedToolPackage负责重新加载并核对产物。

三种编号各有用途：proposalId标识提交材料；validationId标识一次检查；toolId标识正式工具，version进一步标识它的版本。首次发布生成新toolId和1.0.0，不把提案ID直接当工具ID。

正式目录为runtime/tool-artifacts/approved/<toolId>-1.0.0，恰好五文件：

| 文件 | 作用 |
| --- | --- |
| manifest.json | 正式工具说明：身份、版本、名称、运行方式、权限、源码与镜像信息 |
| tool.mjs | 被验证的候选源码，原始字节保持一致 |
| verification.json | 通过验证的完整报告，复制原始字节，不重新序列化 |
| approval.json | 批准人/时间，以及正式manifest和验证报告的摘要 |
| integrity.json | 前四文件各自摘要与整个正式包摘要 |

原提案中的baseline.mjs留在原处。它用于解释“候选比谁改进”，不是正式运行入口。原manifest仍draft，不改写历史材料；新包的manifest为approved。

批准包沿原参考算法：各文件名排序，将“文件名+NUL+该文件SHA-256十六进制+换行”逐项计算总SHA-256。第10C步提案摘要算法保持原样，不能为了统一名字而修改历史指纹。数据库保存正式包摘要，后续加载以它为依据。文件内自带摘要不够：如果一个人同时改了源码和完整性清单，仍应被数据库中的原摘要发现。

写入先在私有临时目录独占创建，文件fsync后只读，最后重命名。Linux文件0400/目录0500。读取检查精确文件集合、普通单链接文件、大小、严格UTF-8、前后文件状态和身份关系。源码最多200000字节、报告16MiB、其他JSON1MiB；损坏JSON错误不回显原内容。Node重命名不提供原子的“不覆盖”标志，当前依靠随机工具ID、目标存在检查和项目私有父目录；不承诺抵抗同UID恶意并发写入。

## 文件二：tool-registry.mjs，让批准成为一致的数据库变化

数据库升级到schema3，新增tool_versions。行内保存工具ID/名称/版本、active状态、来源提案、包目录和摘要、镜像摘要、批准人/时间。runtimeState=retained表示保留运行产物的登记状态，本轮不操作镜像。

activateVersion在同一事务中重新核对：提案仍verified、最新验证ID和报告SHA仍与前置检查相同、材料SHA/工具名/镜像一致、同名版本不存在。之后同时插入版本、把提案改为approved、追加version_activated事件。任何一处失败全部回滚。检查放进事务，是为了防止“检查完后证据变了，却继续批准旧结论”。

已知v1/v2只读查询不会升级；写批准路径显式migrate:true，先用SQLite一致备份保留已提交WAL内容，再升级。v2仍能保存验证记录，避免新功能破坏旧流程。未知库或不符的表结构拒绝。

## 文件三：tool-approval-service.mjs，连接材料、报告、包与登记

approveRegisteredToolProposal负责整个步骤：只读前置检查→显式迁移→生成新包→读回包并再次核对原材料/报告→事务激活→重建目录。

它不只检查passed=true，还绑定具体提案、最新验证编号与字节摘要。首次不合格不会制作正式包。重复批准已approved提案时，重新核对材料、报告和已有包，返回同一个版本，只修复目录；不创建第二个1.0.0，也不增加批准事件，原批准人和时间不变。

文件系统、数据库和目录文件不是一个共同事务，所以必须区分失败点：

| 失败位置 | 已发生什么 | 怎样处理 |
| --- | --- | --- |
| 写包期间 | 可能留下未完成临时包 | 报出路径、保留证据，不标批准 |
| 包成功、DB事务失败 | 包存在，但提案仍未批准 | 保留可定位孤立包；目录不会采用它 |
| DB成功、目录失败 | 版本已active，提案已approved | 明确versionActivated=true；重复批准或重建目录恢复 |

这比仅报一句“批准失败”更准确，否则使用者可能不知道数据库实际上已经完成了批准。

## 文件四：tool-catalog.mjs，生成当前可用版本清单

目录文件是runtime/tool-registry/active-tools.json，协议sirna-tool-catalog/v1。每项包含toolId、toolName、version、directoryName、packageSha256、imageDigest。它是数据库当前active版本的投影，不是另一个可以随意编辑的批准来源。

writeActiveToolCatalog从数据库读取版本，逐个核对正式包和原证据，再原子替换目录文件。readActiveToolCatalog核对文件内容与当前数据库投影；目录缺失但已有active版本会明确报错，不能返回“没有工具”掩盖损坏。catalog-rebuild是显式恢复入口。读取不超过1MiB，输出也不超过1MiB；恢复不依赖损坏旧内容，但仍拒绝链接、目录或多硬链接文件。

当前没有Agent发现/执行函数接线。active-tools.json只是为下一阶段准备可核对清单，不能直接让模型执行任意文件。

## 修改已有查询与命令入口

tool-validation-reports.mjs允许approved提案继续读取最新通过报告，路径/摘要/ID约束不放松。tool-lifecycle.mjs的show会重新核对正式包、原材料和报告，才返回approved/activated=true；附agentCallable=false。

scripts/manage-tool-proposals.mjs沿用服务器Linux/hanwen/指定工作目录限制，新增：

```sh
cd /home/hanwen/Project/project/siNRA-pi
npm run tools:proposals -- approve f742eea2-b025-4474-ae47-d6eab267c408 "hanwen (delegated learning step)"
npm run tools:proposals -- versions
```

approve会写入批准状态，catalog-rebuild会重建目录；versions/version/catalog是读取。版本详情还会核对包。原有list/show/report保持可用。查看已有结果不必重新运行validate:tool，已批准提案禁止再验证，避免静默改变批准依据。
