# 第10F步：正式版本怎样变成可调用的工具

## 本步解决的问题

第10E步的active表示系统登记选择了1.0.0，但还没有一个正式调用入口。本步把目录中的版本转换成AgentTool对象，使用受控容器真正执行，并经宿主机stdio MCP返回结果。它是原仓库正式架构中的后端执行层。

当前网页guest仍运行第9步的固定MCP服务。下一步才连接guest→HTTP后端的动态工具转发与任务身份。本步不改guest镜像、不开放新端口、不重启网页/控制服务、不让任务容器接触Docker socket或登记库。宿主MCP可调用与网页Pi已可调用是两个不同结论。

## 文件一：tool-approved-execution.mjs

discoverApprovedTools({root,runner})是发现入口，返回tools/packages/rejected。它组合上一轮的登记、正式包、原材料、验证报告和目录读回，不扫描未登记的孤立目录。不存在登记库时只返回空列表，不创建运行目录；损坏证据明确进入rejected。MCP看到rejected会报告不可用，避免把损坏伪装成“没有工具”。

每个工具对象有name、label、description、parameters、executionMode和execute。前几项告诉调用者工具是什么、怎么传参数；execute是真正的执行函数。保存代码文件不会自动得到这一层，它需要明确的适配。

例如调用参数：

```json
{"input":{"sequence":"AACCGGTTAA"}}
```

input里是业务参数。外层不能自行加入toolCallId、命令、路径或inputFiles/outputFiles。平台生成UUID调用编号，执行器构造以下stdin协议：

```json
{"protocolVersion":"sirna-approved-tool-call/v1","toolCallId":"平台生成的UUID","input":{"sequence":"AACCGGTTAA"}}
```

validateApprovedToolArguments拒绝未知顶层字段、非JSON值、循环、访问器、代理对象和超过65536字节的业务对象，并生成独立副本，防止调用者稍后修改原对象。JSON对象只是传输合同，sequence的具体生物序列约束仍由该工具代码检查。本步不支持文件转移。

发现时记录toolId/version/packageSha256/imageDigest。调用前重新检查当前目录和全部证据仍匹配；调用后再次检查，发现执行期间正式材料变动也不能报告成功。这不代表抵抗拥有同一系统用户权限的恶意攻击，仍以项目私有目录可信为前提。

成功要求退出码0、未超时/取消/超限、stdout符合单一JSON对象协议，并得到合法文件摘要。失败抛给上层，审计留在服务器。返回内部details含auditPath及包摘要，MCP不把这些私有信息交给业务调用者。

## 文件二：复用tool-validation-runner.mjs的执行内核

本步新增purpose:'approved-call'，改变容器名称、归属标签和事件名称。原默认validation行为保留。名字中的validation反映文件起源，不表示正式调用会重跑整套验证。

正式调用只走run({target:'candidate',...})，不跑基线、语法验证、领域案例和基准门槛，也不改提案批准状态。它仍会检查固定镜像身份、来源标签和镜像实际源码摘要。固定准备助手会把历史baseline文本作为惰性资料写入临时区，但不会执行业务基线。

每次调用新建容器：业务进程用户65534、无网络、无宿主目录/凭据/socket挂载、只读根目录、1GiB内存、64进程、64MiB临时区；CPU配额仍未施加。结束只清理本次获得且归属标签匹配的容器，并确认不存在。不新建镜像，不全局扫描删除容器。

这些措施是当前可信教学工具的受控执行边界，不是任意敌对代码的完整安全证明。工具不会在宿主Node里被import或eval。

## 文件三：tool-run-audit.mjs

审计目录为runtime/approved-tool-runs/<toolName>/<调用UUID>/，每次调用独立保存：

| 文件 | 何时写、表示什么 |
|---|---|
| request.json | 执行前独占写入并刷入文件，记录版本身份、输入摘要和开始时间 |
| audit.json | 执行和清理之后发布终态，记录结果、摘要、策略及清理信息 |

audit协议沿用sirna-approved-tool-audit/v1，保存toolCallId、toolVersion、packageSha256、inputSha256、退出/超时/取消/协议标志、stdout/stderr/output摘要、filesDigest、success。本步另加toolId、imageDigest、executionEvidence和cleanupConfirmed，便于核对真实容器与实际策略。

审计不保存原始业务输入/输出/日志正文。摘要能帮助确认材料一致，不能仅凭摘要恢复输入，也不能认证结果科学正确。验收脚本保存的教学输入输出另属私有验收证据。

请求写不成功就不执行。终态先写独占临时文件、fsync、设为0400，再通过不覆盖目标的硬链接发布；随后移除临时链接，最终文件单链接。fsync失败不能留下一个看似完整成功的audit.json。目录0700，重复UUID/终态写入拒绝，链接和路径重定向拒绝。

如果进程中途崩溃，可能只有request.json而无audit.json，必须视为“不完整”，不能补写成功或自动重跑。进行中收到取消只会在受限执行器完成清理后记cancelled，不保证立即杀死工具；崩溃恢复和孤立容器清理尚未实现。

## 文件四、五：MCP协议与可信宿主入口

apps/mcp/approved-server.mjs接收显式discover回调。每次list/call重新发现；与固定工具名称冲突或目录损坏时明确失败。正式工具标记readOnlyHint=false/idempotentHint=false，因为执行会产生运行审计和临时资源。每个服务实例只接受一个正在运行的正式调用，另一个返回busy；这不是跨进程全局锁。

MCP成功只返回content文本，失败返回isError=true和固定简短提示，不泄露异常里的宿主路径或工具stderr。内部details保留给后端，未来HTTP远程入口也应维持这个边界。工具结果64KiB的JSON经过MCP再次编码可能变大，外层限制为256KiB以覆盖合法编码开销。本步按请求刷新，不声称已实现list_changed主动通知或Pi缓存刷新。

scripts/approved-tools-mcp.mjs仅允许Linux、hanwen、精确项目根、无额外参数和显式项目Docker socket，组装执行器后连接stdin/stdout。启动不调用模型、不执行业务；收到call才执行。npm run tools:mcp供人工启动，MCP自动客户端应直接以Node启动脚本，避免npm横幅混入JSON-RPC stdout。

原apps/mcp/server.mjs仍是guest固定工具入口，两者分开让已有网页任务继续可用。管理CLI的agentCallable=false仍描述网页未接线，不代表这个新后端入口不存在。
