# 第 11A 步：先看懂轨迹，再讨论该造什么工具

## 这一步解决什么问题

上一阶段已经走通“提交工具 → 独立验证 → 看失败反馈 → 一轮修订 → 再验证”。但这些工具任务仍然由人明确提出。原仓库还有更前面的一层：观察 Agent 做事的过程，寻找可能值得封装成工具的重复工作。

这个观察者叫 Curator，可以先理解成“整理证据、提出工具建议的人”。完整 Curator 会调用一个独立 Agent 来判断建议。我们本轮先完成它前面的确定性步骤：从已结束的一轮任务记录中整理工具调用，按固定规则筛出线索，并让网页显示依据。

当前点击“读取本轮预览”只读取旧记录。不调用模型、不运行工具、不生成提案、不批准候选，也不恢复已结束任务的容器。

## 原仓库怎样处理

参考版本固定为 `67d275494c50f1e5c205b96b72a7b1623acfbe1d`，目录 `packages/extensions/tool-curation/`。

| 原文件 | 原职责 | 本轮对应 |
| --- | --- | --- |
| `tool-curation-trace.ts` | 把开始/结束事件配成调用，识别真实 MCP 工具，汇总重复能力，生成有界轨迹 | `tool-curation-trace.mjs` 独立实现只读预览 |
| `tool-curation-coordinator.ts` | 等一轮完成，检查线索，登记请求，启动 Curator，再派发构建 | `tool-curation-preview.mjs` 只实现读取和终态前置检查 |
| `agent-tool-curator.ts` | 独立模型审查，决定 skip/candidate，并检查结构化结果 | 尚未接入 |
| `tool-curation-store.ts` | 保存请求、轨迹、候选及状态 | 尚未接入 |
| `MODULE.md` | 扩展只观察 Task Core 的公共事件，不接管任务运行 | 新增同职责说明 |

原版的确定性门槛是：同一粗分组调用至少 3 次、且输入至少 2 种，或者明确失败至少 2 次。达到门槛只表示“值得审查”。原版后续模型还要判断：是否可复用、是否已有工具覆盖、输入输出边界是否清楚、权限是否合适。

例如，同一个站点上有 3 次不同输入的请求，程序可以发现“重复访问同一站点”。但它不知道这些请求是否应该封装为一个工具：下载数据和提交订单可能同属一个站点，却是完全不同的事情。这正是下一阶段审查的职责。

## 请求怎样经过各个文件

```text
网页选中任务，点击读取
  → GET /v1/tasks/:taskId/curation-preview
  → tool-curation-preview.mjs 检查任务、轮次终态和正式目录
  → TaskStore.readRunEvidence 读取这一轮公共事件及用户消息
  → tool-curation-trace.mjs 配对、排除、分组、筛选、脱敏和限量
  → public/curation.mjs 显示结果及事件依据
```

这一整条路径由程序执行，模型没有参与。它不会因为看到失败记录就自行发送修订消息，也不会把“满足筛选条件”写入候选登记库。

### 1. Task Core 提供有界读取

`packages/task-core/task-store.mjs` 新增 `readRunEvidence(taskId, runId)`。旧接口会返回一个任务的全部事件；新接口只读取指定一轮。

它先统计事件数量和正文 UTF-8 字节大小，超过 2000 条，或事件 payload JSON 加用户消息正文超过 4 MiB，就拒绝部分分析。这个源记录预算不包含事件编号、时间等元数据；最终响应另有完整 64 KiB 上限。限制内再读取事件和唯一绑定的用户消息。整个读取使用同一个 SQLite 读事务，避免数量检查和真正读取来自不同的数据库快照。

没有新增表、修改 schema 或改变消息保存流程。超过上限的结果是“无法分析”，不是“没有线索”。

### 2. 预览服务检查能否分析

`packages/extensions/tool-curation/tool-curation-preview.mjs` 先检查任务存在且没有运行中，再选择指定 runId，默认使用任务保存的当前 runId。它不会悄悄回退到另一轮。

没有执行过的任务返回 `no_run`；不存在的任务或轮次返回 404；缺少终态、绑定不一致返回 409；记录过大返回 413；当前正式工具目录无法核验返回 503。这里特别兼容真实 TaskMessageService：done 后仍可能保存 workspace_synced/workspace_warning 文件归档通知，不能把这类正常轮次误判为未结束；终态后的业务调用仍拒绝。目录失败时不能假装“没有已有工具”，否则会把已有能力错当成缺口。

`apps/api/bootstrap.mjs` 把 TaskStore 和当前正式工具名称注入这个服务。目录沿用 `getRegisteredToolCatalog` 的只读身份核验逻辑，包含固定的 `enumerate_sirna_candidates` 和当前正式工具名称；读取目录不会执行这些工具。

### 3. 轨迹整理区分外层 MCP 与真正工具

`packages/extensions/tool-curation/tool-curation-trace.mjs` 处理两个层次：Pi 看到的工具可能只叫 `mcp`，但它里面真正调用的可能是 `summarize_target_sequence`。

典型保存输入如下：

```json
{"toolName":"mcp","args":{"tool":"sirna_tools_example","args":"{\"value\":2}"}}
```

代码要解析外层工具名、服务前缀及内层 JSON 参数。`connect`、`describe` 只是连接或查询说明，不是执行业务能力，不能混进“重复做了同一件工作”的统计。

开始和结束记录必须属于同一个 task、run、用户消息，工具调用编号和名称必须一致。没有结束、重复编号、重复结束、顺序冲突不能算成功；可识别的 MCP 内层 `isError` 也会被检查。这里只是在解释保存记录中的错误标记，不证明业务结果正确。

### 4. 分组与门槛都不是智能判断

有 URL 的输入按站点粗分组；shell 类操作按开头程序粗分组；其他按工具名分组。相同对象字段换顺序不会被当成一种新输入。无法可信解析或已经被截断的输入，不能凭摘要制造“不同输入”的证据。

普通 read/write/edit、Goal/Builder/验证控制操作、MCP 元操作和已有正式工具按名称排除，不回传其输入输出。在原版中，普通文件操作主要由后续模型提示排除；因为我们现在还没有那一步，本轮提前保守排除并明确记录这个差异。

已有工具按名称排除也有边界：程序没有理解两个不同名字的工具是否语义等价。

### 5. 预览有窗口，不能冒充完整原始轨迹

筛选使用上限内的完整一轮记录；网页只保留最后 12 个业务调用、最多 20 组线索，并显示省略数量。被排除的调用另保留最后 20 项的名称、开始事件 ID 和原因，不包含输入输出，便于理解为什么没有进入筛选。触发线索的部分事件不在显示窗口时，会明确标记依据未完整展示，不能据此声称已准备好完整的模型审查材料。

最终预览含摘要在内最多 64 KiB。常见敏感字段、嵌入 JSON 的敏感字段、URL 用户名密码、查询值和 fragment 会被处理；这不是所有私人文本的完美脱敏，文件路径、业务文本等仍可能含私人信息。页面用文本节点渲染，不把工具返回内容当 HTML 执行。

Task Core 入库前已经可能脱敏和截断，因此输入摘要指“保存记录中归一化输入的摘要”，不是服务商真实原始请求字节的摘要。预览摘要覆盖最终展示对象，用来检查这份预览内容，不是签名、正确性证明或已持久化冻结证明。

### 6. 网页避免串任务

`public/curation.mjs` 实现手动刷新与状态显示；`public/app.js` 在选择任务和任务状态变化时通知它。切换任务或进入新一轮时会清除旧结果、取消旧请求，迟到的响应不能覆盖新任务。

`public/index.html` 新增入口与面板，`public/style.css` 负责布局；`apps/api/router.mjs` 增加 GET 路由和静态模块路由，沿用已有同源限制和 no-store 响应。

## 怎样自己检查

打开现有网页 http://127.0.0.1:3000/，选择一个已经结束的任务，点击顶部“工具线索”，再点“读取本轮预览”。先看轮次编号，再看开始调用数、排除数、不完整数和显示窗口；如有线索，查看具体事件 ID 和输入输出预览。很长的任务目标默认折叠，需要时再展开。

重点练习：同一个任务可能有多轮消息，预览默认只看保存的当前一轮；页面里的“未满足条件”不等于没有潜在可复用能力，只表示这套固定规则没有筛出来。

测试入口：`node --test tests/tool-curation-trace.test.mjs tests/tool-curation-preview.test.mjs tests/curation-ui.test.mjs`。测试使用合成事件和临时数据库，不把人工正例算作真实 Agent 发现。

## 这一次实际验证了什么

服务器有 16 个保存任务。本轮对每个任务重复读取：14 个生成预览，2 个准确返回尚无轮次；14 个当前轮次均没有达到门槛。最终一轮验收比较默认 runId 和显式 runId 的结果，内容及摘要一致。没有为制造“成功发现”的例子发起付费任务。

例如第10O任务 `d72bc8cc-ea17-4782-a4e6-230042dafff8` 的当前修订轮共有 5 次调用：

| 调用 | 它真正做的事 | 为什么不进入发现筛选 |
| --- | --- | --- |
| create_tool_build_session | 开一个构建环境 | 构建控制操作 |
| write_tool_build_file | 写候选源码 | 构建控制操作 |
| run_tool_build_command | 调试候选 | 构建控制操作 |
| finalize_tool_build | 打包成品 | 构建控制操作 |
| propose_exploration_tool | 提交候选材料 | 提案控制操作 |

所以页面显示“工具开始5、业务调用0、排除5、没有线索”。这不否定上一阶段修订成功，而是说明“造工具的动作”本身不该被这层规则再次建议包装。浏览器实际检查了读取、展开排除清单、切换任务清除旧结果，以及空任务 no_run 提示。

本轮测试结果分开记录，避免把修复前后的运行混为一谈：

- 完整1261项：Windows 1248通过/13平台跳过；Linux 1259通过/2平台跳过，均0失败。
- 之后真实记录发现 Compose runId 为64位十六进制，初版显式查询只接收UUID。新增回归先复现400，再改为支持两种已保存编号；修复后两端38项针对性测试全部通过，并完成真实默认/显式GET一致性验收。
- 最后仅把长目标改成折叠显示，21项UI相关测试通过；新增顶部定位链接由浏览器核验。
- 独立审查发现 done 后归档事件的兼容问题，补正反例修复；针对性复审通过。元操作与业务工具、重复/缺失事件、敏感字段、截断、跨任务绑定、旧响应和只读性均有回归。

私有运行记录使用全新 `runtime/curation-preview-*` 前缀。主要包括 `state-before.json`、`ops-tests-01.json`、`targeted-02.log`、`acceptance-02.json` 与最后的 `sync.json`；这些包含运行证据，留在项目私有runtime，不提交Git。最初保全脚本比较SQLite返回的无原型对象与JSON普通对象时失败；改为规范化和逐组摘要后，保留原baseline并检查通过。没有借此覆盖旧业务记录。

前后检查四个业务数据库的全部schema/行、旧工具材料与工作区、原生会话、正式目录、容器和镜像，均保持一致。模型密钥只检查文件元数据；没有新增模型请求、工具执行、提案、验证或版本。正式 `summarize_target_sequence@1.0.1` 仍active，上一轮通过的修订候选仍待人工批准。

网页后端只在空闲时重启；controller、relay和任务guest未重建。断开的本机SSH隧道已恢复，仍只监听127.0.0.1，不新增公网访问或开机自启。

## 下一步

下一步再对照原版接入持久化的 Curator 请求和冻结证据，调用独立的只读 Curator Agent，要求输出 skip 或有事件依据的 candidate，再验证结果字段、证据引用与去重。

之后才连接既有构建、验证、修订链。当前完成的是“发现前的证据整理与可视检查”，尚不能称为完整工具发现或自动自进化。
