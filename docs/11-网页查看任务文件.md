# 第 7 步：网页查看任务文件

本步解决的问题是：Pi 已经在容器里生成结果，用户怎样从网页找到、查看并拿到那份真实文件？

上一轮完成了停止运行、结束任务与释放容器，文件仍保留在服务器。此前网页只显示对话、工具动态和文件所在路径。本轮增加输入／输出列表、文本预览和下载，接通“生成文件之后”的交付过程。

## 一、先用一个例子理解

统计练习中有两份不同角色的文件：

```text
workspace/
├── input/
│   └── numbers.csv       给 Agent 的原始资料：10、20、30、40
└── output/
    └── result.json       Agent 产生的结果：count=4、sum=100、mean=25
```

对话里说“平均值是 25”，属于回复；`result.json` 是可以独立保存、交给其他程序读取的产物。两者可能不同，因此网页需要真正读取磁盘文件，不能把一段模型回复冒充下载文件。

本轮没有让模型重新做统计，也没有再次安装 Pi。增加的是外围应用的文件交付能力。Pi 负责原有 read/write 工具执行；Agent Compose 继续负责容器；新增服务负责把已存在的文件送到浏览器。

## 二、怎样参考原仓库

阅读的参考提交为 `67d275494c50f1e5c205b96b72a7b1623acfbe1d`，应用代码基准为 `965c53fba4eaa23996f54aa0532c7f6e1064bfd8`。

| 原仓库文件 | 原职责 | 本仓库对应位置 |
| --- | --- | --- |
| `packages/task-core/workspace.ts` | 输入／输出文件、元数据、同步和文件名检查 | `packages/task-core/workspace.mjs`：本轮实现读取职责 |
| `apps/api/router.ts` | 任务文件列表、上传及内容接口 | `apps/api/router.mjs`：本轮实现两个 GET 接口 |
| `public/app.js` | 文件列表、预览、下载等交互 | `public/files.mjs` 管请求，`public/app.js` 管显示 |
| `public/index.html` | 网页中的文件操作区域 | `public/index.html` 右侧任务文件区 |

接口外形沿用原仓库：

```text
GET /v1/tasks/:taskId/files
GET /v1/tasks/:taskId/files/:kind/:encodedName
GET /v1/tasks/:taskId/files/:kind/:encodedName?download=true
```

`kind` 只能是 `input` 或 `output`。嵌套文件 `reports/result.json` 应整体编码成 `reports%2Fresult.json`，服务器只解码一次，再检查每个路径段。

列表的每项保留原字段：`id/name/kind/size/sha256/modifiedAt`。本轮额外返回 `state`，用 `ready/unprepared/unsupported` 区分“有目录”“还没有执行环境”“旧 SDK 暂不支持”。空列表不能同时代表所有这些情况。

有一个刻意保留到后续的差异：原仓库还维护 `task-files/<taskId>/input|output`，把输入同步到 sandbox，再把输出收回归档。我们当前直接读取已经保留的宿主绑定目录，没有建立这份独立归档。因此本轮结束后能读取文件，依赖上一轮的 graceful stop 保留目录；不能据此宣称删除 sandbox 后也能恢复文件。上传、独立归档与同步将在下一步学习时一起引入。

参考仓库未提供明确的应用代码许可，本轮依据接口和职责独立实现，没有复制其应用源码。

## 三、一个点击经过哪些文件

```mermaid
flowchart LR
    A[网页选择任务] --> B[public/files.mjs 发 GET 请求]
    B --> C[apps/api/router.mjs 查任务记录]
    C --> D[task-core/workspace.mjs 查执行元数据]
    D --> E[对应 workspace 的 input 或 output]
    E --> F[返回元数据或文件字节]
    F --> G[网页文本预览或浏览器下载]
```

这条链路不经过大模型，也不需要重新启动容器。

### 1. bootstrap.mjs：把文件服务接入应用

`apps/api/bootstrap.mjs` 原本组合数据库、运行时和 HTTP 服务。本轮增加：

```js
const workspaceFiles = new WorkspaceFiles({ root: projectRoot, agentRuntime });
const server = createAppServer({ taskStore, agentRuntime, workspaceFiles });
```

可以把它理解成把“文件管理员”交给 HTTP 接待员。管理员知道项目根目录和已有运行时，但不负责生成回复。

### 2. workspace.mjs：先确定任务归属，再读文件

`packages/task-core/workspace.mjs` 有三个主要入口：

- `workspace(task)`：利用任务的 `executionSessionId` 读取已保存的运行信息，核对 `sandboxId` 与 `workspacePath`。
- `list(task)`：递归查看 input/output，返回文件名、字节数、修改时间和 SHA-256。
- `read(task, kind, name)`：检查文件类别和名称，然后读取真实字节。

`taskId` 是网页任务编号，`executionSessionId` 是执行记录编号，`sandboxId` 是容器环境编号。不能用其中任意一个直接拼出另一个，更不能让浏览器自行传服务器绝对路径。

日期目录沿用此前从 Agent Compose inspect 返回并保存的 `workspace_path`。本次验收任务的真实位置为：

```text
/home/hanwen/Project/project/siNRA-pi/
  runtime/agent-compose/data/sandboxes/2026/10/19/
    92be151ac547443d743b2c4d4d5c30f45cde0b785d26805d5a370d6209778bd9/
      workspace/input/numbers.csv
      workspace/output/result.json
```

同一目录在 guest 中表现为 `/workspace`。这是绑定挂载：宿主与容器看到同一份内容，不是这一轮又复制了一份。

SHA-256 可以理解成根据文件所有字节计算的指纹。本次浏览器下载的 result.json 与服务器文件指纹一致，说明没有被接口替换、漏字或改写；这不证明模型的数学结论正确，数学正确性仍由独立的统计验收检查。

### 3. router.mjs：把文件转换成网页能够接收的响应

`apps/api/router.mjs` 先检查任务存在，然后交给文件服务：

- 列表请求返回 JSON，网页用它画出文件按钮。
- 预览请求返回 UTF-8 纯文本，最大 256 KiB。
- 下载请求返回原始字节，单文件最大 50,000,000 字节。

`Content-Disposition: attachment` 告诉浏览器保存文件；`inline` 用于文本预览。HTML、SVG 和未支持的类型按附件下载，不能以网页脚本的身份运行。文件响应也有禁止缓存、禁止猜测类型和限制内容执行的响应头。

不是 UTF-8 的文件预览返回 415，但下载仍保留原字节。超过预览上限不会悄悄截断文件，而是提示下载；超过下载上限明确拒绝。

### 4. files.mjs：管理“哪一个请求还是当前请求”

`public/files.mjs` 独立维护文件列表和预览状态。切换任务时先清空旧文件、取消旧请求，再加载新任务。

例如先点任务 A，又马上点任务 B；A 的服务器响应可能比 B 晚到。这里除了取消请求，还用递增的请求编号判断结果是否过期，避免把 A 的文件显示到 B 下。关闭预览、重复点击或刷新也会使旧预览失效。

文件请求和聊天运行分开，不会因为正在预览文件就锁住“停止本轮”或“结束任务”。本次独立审查发现刷新失败可能清空同任务的执行信息，已改为仅在切换不同任务时清空；同任务刷新失败仍保留原来的停止／结束能力。

### 5. app.js、index.html、style.css：把数据变成可操作页面

`public/index.html` 增加右侧任务文件区域；`public/style.css` 管分组按钮、文件卡片和文本预览的布局；`public/app.js` 的 `renderTaskFiles()` 将文件状态显示出来。

文件名和内容都通过 `textContent` 填入，文本预览用 `<pre>`。因此即使文本里含有 HTML 标签，也只是文字。结束任务后输入框不可继续发送，但文件区域仍可查看。

## 四、为什么文件读取还需要保护

若接口直接接收任意路径，`../../docs/auth.json` 就可能越过任务目录。若只检查名称，符号链接又可能指向外部文件。因此本轮同时检查名称、任务目录归属、目录链和文件类型，只接受普通单链接文件。

Linux 服务器还会持有打开的目录描述符，通过 `/proc/self/fd` 逐层定位。这样即使某个目录在检查后被换掉，也不会直接跟着新路径去读其他位置。读取前后检查文件身份、大小、修改时间，检测到变化返回 409，要求刷新。Windows 开发环境采用前后身份检查，不能把它等同于 Linux 的目录描述符保护。

列举最多检查 1000 个条目，累计哈希最多 100,000,000 字节，单文件最多 50,000,000 字节。超限返回 413，不冒充完整列表。运行期间多个文件仍可能在不同时间变化，因此列表不是整个目录的原子快照。

这些检查保护本轮 HTTP 文件出口，并没有给 Pi 的原生 read/write 工具增加严格路径沙箱，也没有建立多用户登录鉴权。服务仍只绑定 127.0.0.1，通过 SSH 隧道使用。

只读验收入口：

```sh
node scripts/verify-compose-task-files.mjs <taskId>
```

该脚本下载文件，与宿主字节、大小和 SHA-256 比较，并检查操作前后任务历史、执行元数据未变。验收证据保留在服务器 `runtime/compose-web/files-*-acceptance.json`；真实内容不提交 Git。新建空任务是本次 UI 验收添加的一条普通任务记录，可供后续学习使用。

本轮没有模型调用，没有新系统安装或管理员操作，也没有停止先前保留的两个 guest。
