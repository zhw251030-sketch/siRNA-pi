# 第 12E 步：验证通过后的批准边界

## 为什么还要有批准

验证回答的是“候选工具在隔离环境中是否通过预先声明的检查”。批准回答的是“是否把这份通过检查的不可变快照发布为当前可调用版本”。两者之间必须保留边界：验证成功不等于已经改变活动工具目录。

## 本轮实现

`packages/extensions/tool-curation/tool-curation-coordinator.mjs` 增加了可选的 `automaticApproval` 开关和 `approveTool` 回调。验证通知为 `passed: true` 时，协调器先把持久化自动化记录置为 `approving`；只有显式打开自动批准且回调返回 `approved: true`、`activated: true`，记录才进入 `completed`。回调失败、返回不完整结果、超出批准预算都会进入 `failed`。重复通知通过内存中的请求集合和持久化阶段检查去重，旧的验证通知不能再次批准已经离开 `validating` 阶段的运行。

`apps/api/bootstrap.mjs` 把已有的 `approveRegisteredToolProposal` 接入回调，但默认只提供回调而不启用自动批准。只有设置 `SIRNA_AUTOMATIC_APPROVAL=1`，验证通过后才会自动调用现有批准服务；未设置时会停在 `approving`，等待人工批准。这一默认值保留了项目原有的人工发布安全边界。

## 与参考仓库的对应关系

参考仓库的 `apps/api/router.ts` 在 `verified` 状态下排队 `approval` maintenance job，`packages/capability-platform/tool-maintenance-worker.ts` 再调用 `approveRegisteredToolProposal`，并由自动化状态机观察 `approved` 后进入 `completed`。个人仓库当前已经有批准服务和验证维护队列，但维护队列只覆盖 validation；因此本轮先把“验证通过 → 持久化 approving → 受控批准回调 → completed/failed”接通，复制参考实现的状态边界，但没有声称已经复制其独立 approval SQLite job/worker。独立批准队列是后续 12F 的架构补齐项。

## 验收

`tests/curation-coordinator-integration.test.mjs` 新增场景：默认开关停在 `approving`；显式开关只接受真实激活结果并对重复通知幂等；非激活结果 fail-closed；重启后从持久化 `approving` 状态恢复；停止后的迟到验证通知不会触发批准。本轮该测试文件 32 项全部通过。
