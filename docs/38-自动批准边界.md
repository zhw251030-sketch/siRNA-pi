# 第 12F 步：持久化自动批准队列边界

## 为什么还要有批准

验证回答的是“候选工具在隔离环境中是否通过预先声明的检查”。批准回答的是“是否把这份通过检查的不可变快照发布为当前可调用版本”。两者之间必须保留边界：验证成功不等于已经改变活动工具目录。

## 本轮实现

`packages/extensions/tool-curation/tool-curation-coordinator.mjs` 保留可选的 `automaticApproval` 开关，但配置了 `toolApproval` 后只生成确定性的 approval request UUID 并入队，不直接调用批准服务。worker 的 durable terminal notification 必须匹配当前 `approving` run 和 `toolApproval.latest()`；成功（`approved: true`、`activated: true`）进入 `completed`，失败进入 `failed`，旧或迟到通知不会改变终态。没有 `toolApproval` 时仍保留 `approveTool` 直接回调，仅用于隔离兼容测试。

`apps/api/bootstrap.mjs` 创建独立的 `ToolApprovalStore` 和 `createToolApproval`，用注册表读取绑定 verified 检查，把 `approveRegisteredToolProposal` 作为 worker 执行函数，并在终态通知后更新协调器。worker 只在 HTTP server 已经 listening 后启动，shutdown 时先 drain/stop 再关闭 store。默认 `SIRNA_AUTOMATIC_APPROVAL=0`；只有设置为 `1` 才会自动入队，未设置时停在 `approving` 等待人工批准。HTTP `POST /v1/tool-proposals/:id/approve` 只校验并入队，返回新 job 的 202 或重复请求的 200。

## 与参考仓库的对应关系

参考仓库把 approval job 与 validation job 放在共享 registry maintenance queue，由 `apps/api/router.ts` 入队、`packages/capability-platform/tool-maintenance-worker.ts` 执行。个人仓库为隔离故障域保留独立 `runtime/tool-approval/jobs.sqlite` 和 `tool-approval-worker.mjs`；它与参考实现共享“HTTP 只入队、worker 执行、durable terminal 再推进状态”的边界，但不声称两边使用同一数据库。

## 验收

`tests/curation-coordinator-integration.test.mjs` 覆盖：默认开关停在 `approving`；自动路径只入队；worker terminal 成功/失败推进状态；重复 HTTP 请求去重；重启从 `toolApproval.latest()` 恢复；旧和迟到通知不会改变终态。第 12F 还保留没有 worker 时的 direct callback 兼容测试。
