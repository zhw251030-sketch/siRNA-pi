# 第10A步：从“能调用一个工具”走向“知道怎样检查一个新工具”

本轮沿原仓库继续工具治理，但只完成其第一个独立阶段：工具提案合同预检。检查器已经有可运行的命令和教学草稿；登记数据库、真正执行验证、审批发布仍属于后续阶段。没有修改网页、MCP工具集合或任务容器。

## 一、为什么下一步要先认识合同

第9步的候选枚举工具是开发者预先写好并装进镜像的固定工具。我们知道它调用哪个函数，并为它编写了检查。

原项目还希望接收新的工具代码，甚至接收工具的改进版本。此时不能只收到一段脚本和一句“这个工具很好用”：还需要知道它接收什么、应返回什么、依赖哪些软件、需要什么权限、怎样判断没有改坏、与什么旧实现比较。

这些约定合在一起，就是工具提案的“合同”。合同是描述和检查依据，不是代码已经运行成功的证明。

原仓库将这些步骤分开：

```text
准备完整提案 → 登记候选 → 在专用环境实际验证 → 批准/发布版本 → Agent发现并调用
```

本轮完成的是最左侧的合同检查。后面的阶段会使用这份合同，但不能因为字段填齐，就把状态写成verified或approved。

## 二、先分清原仓库里三个相似名字

| 参考文件（相对参考仓库） | 真正负责的内容 |
| --- | --- |
| packages/capability-platform/agent-tool-registry.ts | 内存中供Agent使用的可执行工具集合，必须保留execute回调 |
| packages/capability-platform/tool-catalog.ts | 固定外部软件的版本、来源、用途和可用性探测 |
| packages/capability-platform/tool-registry.ts | SQLite中的提案、验证报告、获准版本与调用记录 |

第9步的纯JS候选算法并不是外部软件目录中的一个软件安装包。原正式MCP服务也使用固定工具Map，因此本轮没有为了名字叫“registry”就替换它。

主要参考是应用基准965c53f、参考checkout67d2754中的tool-contract.ts、tool-lifecycle.ts和output-matcher.ts。本轮根据其可观察合同独立实现，没有复制许可证未明确的应用源文件。

## 三、tool-contract.mjs：检查一份提案是否把要求讲清楚

新增 `packages/capability-platform/tool-contract.mjs`。它有三个主要入口：

1. `collectToolContractIssues()`：收集缺失或不完整的字段，指出准确位置，例如 `/testCases/0/expectedOutput`。
2. `validateToolProposalInput()`：进一步检查类型、长度、取值范围、权限与依赖的一致性。
3. `checkToolProposal()`：把前两步组合成统一结果，供命令入口使用。

原合同中的关键字段如下：

| 字段 | 初学时怎样理解 |
| --- | --- |
| name / toolName / description | 给人看的名字、稳定调用名称、能力与限制 |
| runtime / script | 用哪种语言运行，以及完整的候选源码 |
| smokeInput | 一次有代表性的成功业务输入，用于将来的基本运行检查 |
| dependencies | 声明第三方依赖及目标版本；没有则明确写空数组 |
| testCases | 应该满足哪些功能行为，每项包含输入和预期输出 |
| repeatabilityMode | 两次运行应该完全相同，还是允许内容变化但必须满足合同 |
| baseline | 用来比较的旧实现或较有限实现 |
| benchmarkCases / minNetGain | 比较哪些案例，候选至少多通过多少项 |
| permissions | 声明是否需要网络或受控软件；声明本身不授予任何权限 |
| runtimeArtifact | 可追溯的容器运行产物，包括镜像摘要、命令、平台和构建会话 |
| parent | 改进已有获准版本时，说明其工具名和版本 |

`script`本轮始终是字符串：检查非空和大小，不进行eval、动态导入或执行。它即使存在语法错误，也不能由本轮预检断言运行失败或成功；真正语法检查与运行是后续验证阶段的职责。

例如，`controlled_software`声明要调用seqkit时，依赖中必须明确列出对应system包及版本。声明controlled_network时，主机名必须符合规定，不能混入URL路径。它们只是检查声明内部是否一致，本轮不会联网或安装软件。

原合同希望锁定依赖版本，但它的实际预检主要限制版本字符，并禁止`latest`等写法；`next`、`stable`、`1.x`仍可能通过。学习版保留这个参考行为。因此“声明通过”不证明版本可以精确解析、不可变、真实存在或已经安装；以后需要实际依赖验证和可追溯镜像共同提供证据。

未知字段与无法完整用JSON表达的数据会明确拒绝；这是学习版比参考宽松HTTP字段检查更严格的地方。其余字段名称、核心范围、三类权限以及缺项错误类别沿用参考语义。

## 四、tool-validation.mjs：约定以后怎样判断结果

新增 `packages/capability-platform/tool-validation.mjs`。这个模块只接收“已有的结果数据”并判断，不运行工具。

`expectedOutputMatches(actual, expected)`使用原项目的 `recursive-subset/v1` 规则：预期对象中的每个键都要匹配，实际结果可以包含更多键。

例如实际结果是 `{"length":4,"gcFraction":0.5}`，预期 `{"length":4}` 可以通过，而预期 `{"length":5}` 不能通过。

三个容易误解的点：

- 数组要求长度和顺序相同，不是“实际数组包含这些元素即可”。
- `{"a.b":1}`寻找名字真的叫a.b的键，不会自动进入a对象再找b。
- `{"length":{"minimum":4}}`不是“大于等于4”的断言，它要求length本身是相应的嵌套对象。这不是JSON Schema。

其他判据：`validationRunPassed()`判断一份记录是否明确成功；`validationCasePassed()`还要检查预期输出；`validationRunsRepeatable()`比较两次记录。

exact模式要求两次都成功，且stdout、stderr和输出文件摘要一致。contract模式允许两次内容不同，但两次仍必须成功；功能案例、基线比较及其他验证门槛并没有取消。本轮对不完整JS运行记录进一步拒绝，避免缺少字段时出现undefined等于undefined而误判通过；未知模式也不能通过。

这些函数通过测试，只证明“检查规则实现符合约定”，不代表本轮提案已经被执行或通过全部门槛。`toolValidationContract()`集中提供规则说明，后续CLI、验证器可以共享同一份合同解释。

## 五、教学草稿：把抽象字段放在一个文件里理解

新增 `examples/04-tool-contract/proposal.draft.json`，名字为summarize_target_sequence：候选代码描述如何清理单条序列/FASTA并计算长度、GC比例；基线只处理纯DNA。

这是与第9步候选枚举不同的一份教学提案。我们故意选择容易手算的例子：ACGT长4、GC比例0.5；同样的碱基带上FASTA标题并用RNA字母时，期望仍然是4和0.5。

基线的能力被人工限制，只用于学习怎样表达功能差异，不是科研性能比较。`minNetGain:1`只是声明未来至少多通过一项比较案例；本轮没有实际运行候选或基线，更没有证明性能提升。

草稿没有runtimeArtifact，因为我们还没有为它构建真实可追溯镜像。不能填写一个看起来正确的sha256字符串来假装完成这个前提。

## 六、check-tool-contract.mjs：让你亲自运行检查

新增 `scripts/check-tool-contract.mjs`，package.json增加 `check:tool-contract`。在项目根目录执行：

```sh
npm run check:tool-contract -- examples/04-tool-contract/proposal.draft.json --draft
npm run check:tool-contract -- examples/04-tool-contract/proposal.draft.json
```

第一条检查草稿，略过运行产物的必填要求；其余合同仍需完整。第二条默认按原正式MCP入口要求运行产物，因此当前教学草稿应准确指出 `/runtimeArtifact` 缺失。

参考项目存在入口差异：src/mcp-server.ts正式MCP提交要求runtimeArtifact；apps/api/router.ts的HTTP提交调用默认collect选项，未开启同一个必填要求。这里的--draft用于学习该区别，不表示学习仓已经实现原HTTP提交接口。

退出码0表示预检通过，2表示合同缺失或非法，1表示命令、文件或JSON输入错误。所有结果明确包含executed=false、registered=false、activated=false、runtimeArtifactVerified=false。即使用户提供结构正确的镜像摘要，检查器也不会确认镜像存在、归属或运行情况。

命令有1 MiB输入限制，拒绝非普通文件和非法UTF-8/JSON；只打印检查摘要，不回显候选和基线源码，也不创建任务、注册记录或运行产物。

## 七、验证记录与下一步

2026-10-20实际验证如下：

- `tests/tool-contract.test.mjs`：99项，覆盖缺字段定位、边界、权限与依赖一致性、运行产物结构、非法JSON数据。
- `tests/tool-validation.test.mjs`：19项，覆盖字面匹配、数组顺序、严格成功记录、两种重复性模式，以及自定义数组不能在序列化时改变结果。审查发现的数组原型遗漏已先复现失败再修复。
- `tests/tool-contract-cli.test.mjs`：8项，通过真实Node子进程检查退出码、文件限制和不执行源码。测试把会写哨兵文件的源码放入提案，确认检查结束后哨兵文件不存在，源JSON哈希未变。
- 本机完整`npm test`：529通过、4项Linux专属跳过、0失败。服务器Node24.16.0完整回归：533通过、0跳过、0失败；包含原MCP固定工具列举和调用回归。
- 两种命令都在本机与服务器实际运行：`--draft`退出0；默认模式退出2，唯一缺项为`/runtimeArtifact`。两者都明确未执行、未登记、未激活、未验证镜像真实性。
- 服务器10份Compose会话元数据SHA-256与检查前一致；3个运行容器ID/镜像不变；凭据只比较inode/大小/修改时间/权限，没有读取内容。网页`/health`仍ready=true、busy=false。本轮模型请求为0，未重启服务或构建镜像。

完整回归还暴露了一项原有测试的时间竞争：停止检查最后一次查询可能先收到gRPC的`DEADLINE_EXCEEDED`，旧测试只接受外层循环的超时文本。`tests/agent-compose-rpc.test.mjs`现在分别覆盖持续运行与不响应，用精确错误码判定后一分支，并保留任务身份、只发一次停止、实际查询状态和耗时上界检查。先用不响应情形复现旧断言失败，再修改测试；停止运行的生产代码没有改变。

测试过程日志与状态对比保存在私有`runtime/contract-preflight-*`，不进入Git。测试通过证明预检及现有功能回归符合上述范围，不证明示例工具已经运行成功。

下一步应把一份合同对应到真实、可追溯的运行产物，再登记提案并接入独立验证环境。之后才能讨论如何判断通过、批准版本、发现新工具，以及失败后的修订。本轮的预检不代替这些阶段。
